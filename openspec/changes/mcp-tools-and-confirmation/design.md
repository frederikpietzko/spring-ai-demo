## Context

- `POST /chat` takes `ChatRequest(persona, message)`; `ChatController` answers `CLAIMANT` through `ClaimantChat` and `ADJUSTER` with one `Error` (ADR-0005). The terminal-event rule is `onCompletion` (Done) before `catch` (Error). The desktop persona switch lists `Adjuster` disabled; `ChatViewModel` stops collecting at the first non-`TextDelta` event.
- `core-mcp` (landed) serves MCP at `http://localhost:8081/mcp` over legacy Streamable HTTP with `findPolicy`, `getClaim`, `listClaimsForCustomer`, `fileClaim`, `updateClaimStatus`, `issuePayout`; domain errors come back as `isError` results. Seed claim 4711 is `FILED`; `issuePayout` needs `APPROVED`, so the adjuster must call `updateClaimStatus` twice first.
- The shared backend test context (`@IntegrationTest`, `TestInfrastructure`: pgvector container, `FakeChatModel`, `FakeEmbeddingModel`) is bound by ADR-0004. `FakeChatModel.requestTool(name, json)` scripts tool calls with ids `call-1`, `call-2`, ... .
- Other tracks (`session-memory`, `claim-intake`, `observability`) extend `ChatRequest`, `ChatController`, `ClaimantChat`, `ChatViewModel` and `App` in parallel. This plan keeps its footprint in those files to a few lines and puts new code in a new package `backend/adjuster` (same top-level package `backend`, so no ADR-0003 change).
- Spring AI facts checked against the 2.1.0-RC2 sources before planning (re-check what you depend on while implementing): MCP tools are not registered on a `ChatClient` automatically and the global resolver drops them on purpose; `SyncMcpToolCallback` has the default `ToolMetadata`, so `@Tool(requiresConfirmation)` never applies, but `ToolCallingAutoConfiguration.confirmationPolicy` also honours `spring.ai.tools.confirmation.tools` (documented for MCP tools); a paused streaming loop ends with a last chunk holding only the tool-call parts and the metadata key `ToolCallDecisions.AWAITING_DECISION_METADATA_KEY`, and `stream().content()` hides it, so `stream().chatResponse()` is needed; the loop keeps no state, and an allowed call runs only if `prompt.options` carries its callback.

## Goals / Non-Goals

**Goals:** the adjuster calls the core tools; `issuePayout` runs only after an explicit approve; one obvious class per concept; offline tests with fakes.

**Non-Goals:** OAuth, claimant ids, adjuster memory, durable or expiring pending state, per-call decisions (see the proposal).

## Decisions

**D1 - Confirmation by tool name, no wrapper (roadmap R3).** `spring.ai.tools.confirmation.tools: issuePayout` in `application.yaml`. The policy is global to the `ToolCallingManager`, which is harmless because only the adjuster client carries MCP tools. Rejected: a local `@Tool(requiresConfirmation = true) issuePayout` that delegates to the MCP tool: a second tool with the same name collides with the MCP one at request time, and it duplicates the tool's contract.

**D2 - Pause by ending the stream, resume with a new request (roadmap R6).** The adjuster turn streams `chatResponse()`; a chunk whose metadata lists awaiting keys becomes `ChatEvent.ConfirmationRequest(confirmationId, toolName, arguments)`, a **terminal** event (no `Done` after it). `PendingConfirmations` (a `ConcurrentHashMap<String, PausedTurn(conversation, reply)>`, id = UUID) keeps the paused reply on the server: the client never sends a tool call, only `ConfirmationDecision(confirmationId, approved)`. `POST /chat/decisions` takes the pending entry out (so a replay cannot run the tools twice), builds the decisions for every key of the paused reply (`ToolCallDecision.allow` or `deny(key, DENIED_TEXT)`), runs `ToolCallingManager.executeToolCalls(Prompt(conversation, options with the core callbacks and the tool context), reply, decisions)` and streams a new turn from its `conversationHistory()`. That turn may pause again. Everything, including the blocking `executeToolCalls`, runs inside `flow {}` so a failure becomes an `Error` event, not a 500. Which failures end in an `Error` event: `ToolCallingManager` hands a tool's exception to the model as the tool-result text unless the cause is a checked exception or an `Error` (`DefaultToolExecutionExceptionProcessor`, `spring.ai.tools.throw-exception-on-error` is `false` by default; sources 2.1.0-RC2), and `SyncMcpToolCallback` turns every non-protocol exception and every `isError` result into such a text, so the model sees domain errors of `core-mcp` and can answer; only a protocol-level `McpError` (rethrown unwrapped by `SyncMcpToolCallback`) or a checked exception from a `@Tool` method fails the loop. The test therefore makes the fake payout tool throw a checked `java.io.IOException` (a `RuntimeException` would be returned to the model as text, and a missing script would end in the same generic error, a test that passes for the wrong reason); it scripts a model reply after the decision and asserts the model received no prompt after the pause, so a swallowed failure would show up as text. An unknown or already taken id answers one `Error` event ("Nothing is waiting for this decision."). Rejected: keeping the SSE stream open and receiving the decision on a second channel (a held server thread, a correlation channel and a timeout story for a demo); the decision as a field of `ChatRequest` (the same type `session-memory` and `claim-intake` extend; a separate endpoint reads clearer on a slide and merges trivially).

**D3 - One `AdjusterChat` class.** `stream(message)` and `decide(decision)` share a private `turn(...)`; both build the whole request (the `prompt()` spec, the tool callbacks, the tool context) **inside `flow {}`**, unlike `ClaimantChat`: `.stream()` builds the request eagerly (`DefaultChatClientUtils.toChatClientRequest` lists the MCP tools, which is the lazy `initialize`, and validates the tool names), so built outside the `flow` an unreachable core (`RuntimeException` "Client failed to initialize listing tools") or a duplicate tool name would be thrown from the controller method and become an HTTP 500 instead of an `Error` event; `PendingConfirmations` is a separate tiny class so tests can see it. `ChatController` gets the `ADJUSTER` branch and the decisions endpoint; the terminal rule becomes "Done unless the stream ended in a `ConfirmationRequest`" (the controller remembers whether the last event was a confirmation request; `Error` handling is unchanged).

**D4 - The resumed conversation is just the user message.** `PausedTurn.conversation = [UserMessage(message)]`; rounds that already ran before the pause (for example `getClaim`) are not in the paused reply and are lost on resume, so the model sees user, its own paused tool request, the tool result. Anthropic accepts that order. No `SystemMessage` goes in it (the client adds `defaultSystem` on every request; a stored one would double it). Rejected: an in-loop recorder advisor storing the full history (more machinery for a demo whose pause is the last step of a short flow); adopting `session-memory` (claimant-only by its design).

**D5 - Deny is a tool result, not a cancel.** Spring AI 2.1 has no cancel primitive. Deny means `ToolCallDecision.deny(key, "The adjuster did not approve this payout.")`: no tool runs, the model receives the text as the tool result and writes a closing reply (the test scripts one more fake reply). Approve or deny applies to every call of the paused reply, because the manager requires a decision for each.

**D6 - Explicit registration, a second `ChatClient`.** `adjusterChatClient` = builder + `defaultSystem(prompts/adjuster-system.md)` + `defaultToolCallbacks(@Qualifier("mcpToolCallbacks") ToolCallbackProvider)`. With two `ChatClient` beans `ClaimantChat` resolves only by parameter name today, so it gets an explicit `@Qualifier("claimantChatClient")` (closes a follow-up in `decisions.md`). The adjuster prompt names the demo flow: a `FILED` claim must be moved to `UNDER_REVIEW` and `APPROVED` with `updateClaimStatus` before `issuePayout`, and `issuePayout` waits for a human.

**D7 - Lazy MCP connection.** `spring.ai.mcp.client.initialized: false` and `spring.ai.mcp.client.streamable-http.connections.core.url: ${CORE_MCP_URL:http://localhost:8081}`; the endpoint default `/mcp` matches. With the default `initialized: true` the backend would fail to start whenever `core-mcp` is down; lazily, the first adjuster request connects (a failed attempt resets and retries). Claimant chat and the rest of the backend never need the core. Starter: `spring-ai-starter-mcp-client` (JDK `HttpClient` transport; the WebFlux variant would pull a second web stack into an MVC backend); no catalogue entry (the BOM manages it).

**D8 - Caller identity is a fixed adjuster identity for now.** Every adjuster request sets `toolContext(mapOf("actor" to "adjuster-agent"))`, on the first turn and on resume. The default converter forwards the whole context to `core-mcp` as MCP `_meta`, so the values must be small, JSON-able and non-secret; `core-mcp` ignores `_meta` until `mcp-security`. `ChatRequest` has no claimant id and the claimant gets no tools, so the roadmap's "claimant identity through `ToolContext`" is delivered as the mechanism plus this fixed identity; the claimant id arrives with `claim-intake`/`mcp-security` (ADR-0009). Rejected: inventing a customer id field in `ChatRequest` now (a protocol change nobody consumes yet).

**D9 - Tool-name collision policy.** MCP names stay exactly as `core-mcp` publishes them, and the confirmation property uses the same names. The MCP auto-configuration registers `DefaultMcpToolNamePrefixGenerator` (`@ConditionalOnMissingBean`), which renames a name that is already taken to `alt_N_<name>`, keyed by (client, server, `Tool` record): a re-listing after a changed `Tool` record, or a second connection publishing the same tools (likely with `mcp-security`'s per-persona clients), would turn `issuePayout` into `alt_1_issuePayout` and `forTools("issuePayout")` would silently stop gating the payout. So `McpClientConfiguration` (a small `@Configuration` in `backend/adjuster`) declares `McpToolNamePrefixGenerator.noPrefix()` as a bean; the default then backs off, names stay as published and duplicates fail fast in `SyncMcpToolCallbackProvider.validateToolCallbacks` (`IllegalStateException`, sources 2.1.0-RC2). Local `@Tool` names must not reuse a core name: Spring AI throws at request time for duplicate names in one request. That exception comes from the same request-building step as an unreachable core and both are thrown inside `flow {}` (D3), so both end in an `Error` event; one `/chat` test pins that path with a failing tool listing (the fake provider can be told to throw), the collision itself is pinned at the `ChatClient` level (no production local tool exists to collide through `/chat`). The generator test (offline, `McpClientWiringTest`) asks the context's generator for `issuePayout` of two different connections and expects the name unchanged both times. Rejected: a `McpToolNamePrefixGenerator` such as `core_` (it changes the D12 contract names of `core-claims-mcp`, and the property would have to say `core_issuePayout`); keeping the default generator (the silent `alt_N_` rename above); an `McpToolFilter` "local wins" (hides a mistake).

**D10 - Test seam: client off, fake provider under the real bean name.** `@IntegrationTest` gets `spring.ai.mcp.client.enabled=false` (no client, transport or provider bean, nothing touches the network). `TestInfrastructure` declares `@Bean mcpToolCallbacks(FakeCoreTools): ToolCallbackProvider` built with `MethodToolCallbackProvider`; the production `@Qualifier("mcpToolCallbacks")` resolves to it. `FakeCoreTools` has `@Tool getClaim(claimNumber, toolContext: ToolContext)` and `@Tool issuePayout(claimNumber, toolContext: ToolContext)`: `MethodToolCallback` hands the context only to a `ToolContext` parameter, so both fakes declare one (and `validateToolContextSupport` throws `IllegalArgumentException` when such a method gets an empty context, so a missing `actor` fails loudly). `getClaim` is the tool the identity scenario reads, because `issuePayout` is gated and does not run before a decision. The fake records calls, can be told to make `issuePayout` throw a given exception and to make the tool listing throw (both needed by D2 and D3), and is reset before each test with the chat model (extend `FakeChatModelReset`). The provider bean is a small `ToolCallbackProvider` that throws the configured listing failure and otherwise delegates to a `MethodToolCallbackProvider`. It does **not** set `requiresConfirmation`: confirmation must come from the committed property, exactly as for the real MCP callback. A separate `ApplicationContextRunner` test (like `OllamaWiringTest`) loads the MCP client, tool-callback, transport and tool-calling auto-configurations with the committed YAML and asserts: the connection `core` has the default URL (the test JVM has `CORE_MCP_URL` scrubbed, see the task list), one `SyncMcpToolCallbackProvider` exists, startup succeeds with no server, the context's `McpToolNamePrefixGenerator` returns `issuePayout` unchanged for two different `McpConnectionInfo`s, and the `ToolCallingManager` bean gates `issuePayout` and not `getClaim` behaviourally. There is no `ToolCallConfirmationPolicy` bean (`ToolCallingAutoConfiguration` builds the policy inside the `toolCallingManager` bean from `ToolCallingProperties.Confirmation` and optional policy beans, and `confirmationPolicy(...)` is package-private), and binding the properties would only prove the YAML key. So the test calls `executeToolCalls(prompt, response)` with a prompt whose `ToolCallingChatOptions` carry an `issuePayout` and a `getClaim` callback and a response holding the call: `ToolCallConfirmationRequiredException` for `issuePayout`, the result of the tool for `getClaim`. The runner also loads `McpClientConfiguration` (the `noPrefix()` bean). Accepted gap, a deviation from the roadmap entry's test boundary ("a real `core-mcp` started for the test or a fake MCP server"): `SyncMcpToolCallback` itself (argument JSON to `CallToolRequest`, `isError` to text, `_meta` forwarding, the lazy `initialize`) is not run in the suite; `core-mcp`'s tests cover the server, and the manual smoke (task 6.2) covers the wire. Rejected: a fake MCP server inside the backend context (the client transport is built before `local.server.port` exists; a server starter in backend tests changes the shared context); starting `core-mcp` out of process (a second application plus a database container, and the backend would be wired to the `core-mcp` module).

**D11 - Protocol shapes.** `ConfirmationRequest(confirmationId: String, toolName: String, arguments: String)` with `@SerialName("confirmation-request")` (no field called `type` or containing `token`); `ConfirmationDecision(confirmationId: String, approved: Boolean)`. When several calls are gated the event shows the first one; the decision still covers the whole paused reply (D5).

**D12 - Desktop.** `ChatApi` gets `decide(decision): Flow<ChatEvent>`; `HttpChatApi` shares the SSE reading with `send` (one private function for the URL and body). `ChatState` gets `pendingConfirmation: ChatEvent.ConfirmationRequest?`; `ChatViewModel` sets it on the event (and `sending=false`), ignores `send` while it is set, and `decide(approved)` posts the decision, clears the pending state and appends the continuation to the same reply. `App` shows a `ConfirmationPanel` (tool name, arguments, `Approve` and `Deny` `DButton`s) above the input row and enables `Adjuster` in the persona switch. Ordinary and decision streams share one collect function so both end on the same terminal-event rules.

**D13 - Docs, no new ADR.** ROADMAP section 6 assigns no ADR to this change, and no new top-level package or shared abstraction is added. ADR-0005 gets a status-line note and a dated addendum (the `ADJUSTER` answer, the `ConfirmationRequest` terminal event, `POST /chat/decisions`, the stateless-loop consequences). ADR-0004 describes the shared test context this change alters, so it gets a status-line note and a dated addendum as `policy-rag` did for the fake embedding model (the MCP client is off in tests, the fake core tools live under the real bean name `mcpToolCallbacks`, the D10 gap is stated, and the Test task scrubs `CORE_MCP_URL` like the provider credentials). `decisions.md` records D5, D8 and D10 as deviations from the roadmap entry: deny is a tool result and not a cancel (D5), a fixed `actor=adjuster-agent` replaces a claimant identity (D8), and the fake provider replaces a real or fake MCP server (D10); the README and the stale specs (backend-chat, desktop-chat, chat-protocol) are updated through the deltas.

## Risks / Trade-offs

- **Pending entries leak** if a decision never arrives (an in-memory map, demo only); a restart drops them and a late decision answers "nothing is waiting".
- **Lost earlier tool rounds** on resume (D4): the model may re-run a read tool before it answers; harmless for read-only tools.
- **Global confirmation policy** (D1): any future tool named `issuePayout` would be gated too; intended.
- **Merge hotspots** with the other tracks: `ChatController`, `ChatConfiguration` (new bean only), `ClaimantChat` (one annotation), `application.yaml`, `build.gradle.kts`, `ChatViewModel`, `ChatApi`, `App`, `TestInfrastructure`, `IntegrationTest`, `backend/build.gradle.kts` (test environment scrub), `EndpointsTest`, ADR-0004, ADR-0005, README. After the merge the adjuster client should adopt the observability advisors; session advisors are deliberately not added (claimant-only).
- **Model behaviour**: with a real model, whether it follows the review-approve-pay order is up to the prompt; tests script the model, the smoke only checks the plumbing.
