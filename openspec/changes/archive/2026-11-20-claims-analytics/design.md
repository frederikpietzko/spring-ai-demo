## Context

- `core-mcp` serves six tools; each tool class is an `@Component` with `@McpTool` methods returning `CallToolResult` through `ToolResults.ok/error`; services in `coremcp.domain` use Exposed and return sealed results (strings such as ISO dates are parsed in the service). The seed has three `FILED` claims and no payout; tests write only on the sandbox policy `KP-9000` (district `NEON_MARKET`, a `RIVERSIDE` claim in `ClaimToolsFileTest`).
- The adjuster (landed in `mcp-tools-and-confirmation`) gets the core tools from the `mcpToolCallbacks` provider as `defaultTools` of `adjusterChatClient`; `AdjusterChat.turn` builds the request inside `flow {}`, streams `chatResponse()` and emits `TextDelta`/`ConfirmationRequest`. The backend tests use `FakeCoreTools` behind a provider named `mcpToolCallbacks`.
- Checked against the 2.1.0-RC2 sources (re-check what you depend on): the tool loop (`ToolCallingAdvisor`) never streams tool results, only the final text and a paused chunk; `SyncMcpToolCallback.call` returns `jsonHelper.toJson(response.content())`, so the model and the backend see `[{"text":"<the core's JSON as a string>"}]` (no `type` field, `structuredContent` dropped, and a result with empty `content` reaches the model as `[]`); `isError` results throw `ToolExecutionException`, which the manager turns into the model's tool result; `.tools(ToolCallbackProvider)` on a prompt is resolved lazily per request; a `ToolContext` entry is forwarded to the core as MCP `_meta` and must stay JSON-able; `@McpToolParam` defaults to `required = true` even on nullable fields, and a missing argument arrives as `null`.

## Goals / Non-Goals

**Goals:** typed, read-only aggregate tools with no free SQL; a table in the desktop that comes from the tool result and not from the model's prose; one obvious class per concept; offline tests with fakes.

**Non-Goals:** charts, month grouping, scopes (`mcp-security`), a table for `countClaims`, tables from a confirmed (resumed) batch.

## Decisions

**D1 - Two tools, one data-class filter, JSON text results.** `AnalyticsTools` (own class, so `mcp-security` can put `analytics:read` on it) has `countClaims(filter)` and `payoutStats(filter, groupBy)`, both `readOnlyHint = true`. `ClaimFilterInput` is a data class whose fields are nullable with `@field:McpToolParam(description, required = false)` written out (without `required = false` the schema marks them required); `filter` itself stays required, and its `@McpToolParam` description (on both tools) tells the model to send `{}` for "all claims". The hint lives in the tool description and not in the system prompt: the prompt is rendered as a template whose delimiters are `{` and `}` (D6), while tool descriptions are not templated. A missing non-null `filter` would arrive as `null` and make Kotlin throw an NPE inside the core's `SyncMcpToolMethodCallback`, which catches every `RuntimeException` and returns an `isError` result, so the model gets a tool error it can retry, not a hard failure; the description makes that rare. `groupBy` is a nullable enum `StatsGrouping { DISTRICT, KAIJU_CLASS }` (`STATUS` is not offered: only a payout sets `PAID` and `payoutStats` joins `Payouts`, so it could only ever return one `PAID` row; `status` stays a filter field, shared with `countClaims`, where it matters). Results are `ToolResults.ok(json, ...)`: `{"count":n}` and `{"groupBy":...,"groups":[{group,payouts,totalPaidMinor,averagePaidMinor}]}`. Rejected: `generateOutputSchema`/`structuredContent` (the backend's MCP client forwards only `content`, so the model would see `[]`); separate filter parameters per tool (the same five parameters twice on a slide).

**D2 - `AnalyticsService` with Exposed aggregates.** `ClaimFilter(district, kaijuClass, status, from: String?, to: String?)` and sealed results (`Counted`/`Stats` and `Invalid(message)`) in `coremcp.domain`, like `FileClaimRequest`/`FileResult`. One conditional `andWhere` per given field (not `compoundAnd`, which throws on an empty list). The period applies to `Claims.incidentAt`: `from` is the start of that UTC day, `to` is exclusive start of the next UTC day. `payoutStats` is `Claims innerJoin Payouts`, `count` and `sum`, and the average is computed in Kotlin from them as `BigDecimal(total).divide(BigDecimal(count), 0, RoundingMode.HALF_UP).toLong()` (not `avg(0)`: Exposed's `Avg` column type is a `DecimalColumnType` whose `valueFromDB` already rounds half to even, so a later "half up" would do nothing and 2.5 would become 2), `groupBy` the chosen column and `orderBy` it; no grouping selects a single aggregate row whose label is `ALL` and returns no group when nothing matches (the sum is `null`). Rejected: month grouping (time-zone rules for a demo), a `sumOf`/`groupBy` in Kotlin over loaded rows (aggregates belong in SQL and on the slide).

**D3 - A claims history seed, separate from the fixtures.** The roadmap tests "against seed data" and the seed has no payout, so a demo question would answer "nothing". A hand-written migration (`V20261121000000__seed_claims_history.sql`, the old migration is checksummed) adds customers 101-103, policies `KP-2001`-`KP-2003` and claims 4601-4612 (table in the `core-claims-mcp` delta), districts `HARBOUR`/`OLD_TOWN`/`HILLTOP`, repeats the `setval` lines, and uses ids high enough not to collide with seed rows of other changes. Claim numbers stay below 4711; customers 1-5 and `KP-1001`-`KP-1004` are untouched so the fixture scenarios do not change. The dates are fixed (November 2026), so "this month" drifts away when the demo runs later: ask for "November 2026" then, or move the dates; relative dates (`now() - interval`) would make the tests non-deterministic. Costs: `SeedFixturesTest` ("exactly five customers", "only claims 4711 to 4713 are on fixture policies") is narrowed and the fixtures requirement (like the tool catalogue) is replaced by a renamed one through REMOVED + ADDED, because a MODIFIED block cannot rename its scenarios and "Six tools are listed" / "Fixtures are the only seed" would be wrong in the archived spec. Rejected: no seed and tests that file their own claims only (works for tests, but the demo has no numbers). Payout tests that must be exact use a unique incident day on the sandbox policy (file, approve, pay, then filter on that day) because sandbox payouts on `NEON_MARKET` accumulate in the shared database.

**D4 - The table is captured in the backend, by a per-request decorator.** Spring AI 2.1 never streams tool results, so the table cannot come from the stream. `TableCapture(delegate: ToolCallback, onResult: (String) -> Unit)` implements `ToolCallback` explicitly (definition and metadata of the delegate, so the name and the confirmation/collision rules stay; no Kotlin `by` delegation, which does not cover Java default methods). It overrides `call(input, toolContext)`, the overload the tool manager invokes, and passes the context to the delegate (`call(input)` forwards to it with `null`), so the `actor` entry still reaches the core as `_meta`. The delegate runs first; an error result throws before the hand-over, so it is never captured. The hand-over runs after the delegate returned and must never throw out of `call` (`DefaultToolCallingManager` catches only `ToolExecutionException`, so any other exception would fail the whole reply with the generic `Error` event): the mapping and the `trySend` sit in a `try`/`catch`, a mapping failure (for example `[]` or a non-JSON string) is logged and emits no table, `payoutStatsTable` returns `null` for an unexpected shape, and a `trySend` that does not succeed (closed or full channel) is logged. The delegate's result always goes back to the model unchanged. `AdjusterChat.turn` becomes a `channelFlow` that builds a `ToolCallbackProvider` lambda wrapping only `payoutStats` and passes it with `.tools(provider)`; the callback does `payoutStatsTable(result)?.let { trySend(it) }` (guarded as above). Ordering is deterministic: the tool runs (on a bounded-elastic thread) and sends before the next model round streams, so the table precedes the answer text (the text after the tool call; a short lead-in the model may write before the call in the same round streams earlier, before the tool runs, and so comes before the table); `Done` follows from `ChatController` as for any reply. Consequence: `defaultTools(coreTools)` is removed from `adjusterChatClient` (otherwise every core name is registered twice and the duplicate-tool rule fails the request); the provider is still resolved lazily inside the flow, so an unreachable core is still one `error` event. `ToolContext` stays `{actor}` only. Rejected: a sink object in the `ToolContext` (forwarded to the core as `_meta`, so it would have to be stripped, and it breaks the "exactly `{actor=...}`" tests); `returnDirect` (the model would write no answer and the chunk would need special parsing); subclassing `ToolCallingAdvisor` through its protected hooks (too clever for a slide); an observation handler (only correlates through the Reactor context). Accepted gap: the resumed batch (`decide` -> `runToolCalls`) uses the plain callbacks, so a `payoutStats` call in a confirmed batch gives no table; `payoutStats` is never gated, so this needs a payout and an analytics call in one model reply.

**D5 - One generic event, mapped from the core's JSON.** `ChatEvent.AnalyticsTable(title, columns, rows: List<List<String>>)` (`@SerialName("analytics-table")`, non-terminal in `isTerminal`, ADR-0005 addendum). All cells are strings so the desktop needs no domain knowledge; amounts are minor-unit digits. `payoutStatsTable(json, result)` (backend, small and pure) reads the wire string with the Boot `JsonMapper` (Jackson 3): `readTree(result)[0]["text"]` is the core's JSON, parsed again; every missing node (an empty array, no `text`, no `groups`) makes it return `null` (no table) instead of throwing. The title and column names are built there (see the `adjuster-tools` delta). Rejected: a typed `PayoutStats` event with `Long` amounts (the desktop would need chart code for little demo value); parsing the model's prose (not a structured result).

**D6 - Today's date in the adjuster prompt.** Same pattern as the claim intake: `Today is {today} (UTC).` in `prompts/adjuster-system.md` and `.system { it.param("today", LocalDate.now(ZoneOffset.UTC).toString()) }` on every `turn`. The whole prompt becomes a template (`StTemplateRenderer`, delimiters `{`/`}`, and it only logs compile errors, so a stray brace is silently mangled and no test notices), so it holds exactly the one `{today}` placeholder and no other `{` or `}`; a test reads the raw resource and asserts that. One added instruction: counts, payouts and statistics come only from `countClaims` and `payoutStats`, never from the model's own arithmetic; dates are `yyyy-MM-dd`; "an empty filter object means all claims" is said in words only if at all (the literal `{}` hint is in the tool description, D1). Rejected: a date tool (an extra round trip for a constant).

**D7 - Desktop.** `ChatMessage` gets `analyticsTable: ChatEvent.AnalyticsTable?`; `ChatViewModel` stores it on the reply (a new branch of the exhaustive `when`); `MessageBubble` renders a `Column` of `Row`s with `Modifier.weight(1f)` cells (compose-foundation has no table widget; no new library) and counts the table as content for the "…" placeholder. A bar chart is out of scope.

## Test boundaries

- **`AnalyticsService` (core-mcp, `@CoreMcpIntegrationTest`, real PostgreSQL, the seed history):** catches wrong filters, period bounds, grouping, ordering, rounding (including a `.5` average, half up) and invalid input; misses MCP argument binding and the schema.
- **MCP endpoint through `McpTestClient` (core-mcp):** nested-map arguments (`{"filter":{...},"groupBy":"..."}`), required/optional schema, result JSON and `isError` shape, the tool catalogue (`ToolCatalogTest`: eight tools, five read-only); catches annotation mistakes (a field accidentally required, the `{}` hint missing from the `filter` description); misses nothing of the service.
- **`chat-protocol` unit:** JSON round trip and `isTerminal` of the new event.
- **Mapping unit (backend):** `payoutStatsTable` on the exact wire string (grouped, ungrouped, empty); catches a wrong parse of the double-encoded shape and a throw on an unexpected shape (`[]`, no `text`, not JSON); misses ordering in the stream. A small `TableCapture` unit test (delegate answering `[]`) asserts that `call` returns the delegate's result unchanged, throws nothing, emits nothing, and hands the tool context to the delegate.
- **`POST /chat` with `FakeChatModel` + `FakeCoreTools` (backend, shared context):** `payoutStats` requested -> events `[AnalyticsTable, TextDelta, Done]`, tool recorded with the `actor` context, tool offered once, `countClaims`/`getClaim`/failed call give no table, prompt has today's date; catches the decorator, ordering and duplicate registration; misses the real `SyncMcpToolCallback` (the fake returns the wire shape that was verified in a REPL against the real MCP types, and the manual smoke covers the wire).
- **Desktop (`ChatViewModelTest` with `FakeChatApi`, one semantics test):** the table is stored, the reply ends, the cell texts are on screen; misses real layout.

## Risks / Trade-offs

- The `from`/`to` period is on the incident day in UTC; a claimant's local day can differ (demo simplification).
- Fixed seed dates drift from "this month" (D3). The History seed ids (101+, 4601+) could clash with seed rows another change adds; the merge shows it as a Flyway error, not silently.
- The exact aggregates depend on a convention: sandbox claims are filed only in `NEON_MARKET` or `RIVERSIDE`, never in the history districts `HARBOUR`, `OLD_TOWN` or `HILLTOP`. It is written down in ADR-0004 (module `core-mcp` section), the requirement "Claims history is seeded for analytics" and a KDoc note on `aClaimRequest`; nothing enforces it.
- `payoutStats` names are a contract of the capture: renaming the tool means changing one constant in the backend (a test fails otherwise).
- No manual smoke with a real key is possible in an unattended run; the REPL-verified wire shape and the fake are the safety net.
