## Context

- The vector store (ADR-0006) is one pgvector table `vector_store` with a `corpus` metadata field; `sighting-bulletin` was reserved for this change. `PolicyWordingIngestion` is the pattern for ingestion (one `embed` call, then `upsert` with stable ids, fail fast). `ClaimIntake` is the pattern for a private chat client with a blocking `entity<T>()` call and a sealed result.
- `mcp-tools-and-confirmation` landed: `adjusterChatClient` (system prompt plus `coreTools`, the `@Qualifier("mcpToolCallbacks")` provider), `AdjusterChat` (streams, sends `toolContext(actor=adjuster-agent)`), `FakeCoreTools` under the real provider bean name. Seed claim 4711 is `FILED`, `HARBOUR`, `2026-11-18T15:00:00Z`, class 3; 4712 is `OLD_TOWN` `2026-11-16T09:30:00Z` class 5; 4713 is `RIVERSIDE` `2026-11-17T18:10:00Z` class 1.
- Spring AI has no retrieval tool: agentic RAG here is a hand-written `@Tool` around `vectorStore.similaritySearch` (checked against the 2.1.0-RC2 sources). Everything needed is on the backend classpath already.

## Goals / Non-Goals

**Goals:** the model decides when, where and how often to retrieve; time and place are metadata filters; the fraud verdict is typed; claim 4711 is flagged; offline tests against real pgvector.

**Non-Goals:** the subagent split, a desktop verdict, claim-history comparison, real-model quality (see the proposal).

## Decisions

**D1 - One new package `backend/fraud`, no ADR.** `SightingBulletinIngestion`, the corpus reader (D2), `SightingBulletinSearch` (the tool), `FraudCheck`, `FraudAssessment`. Same top-level package `backend`, like `intake` and `rag`; ROADMAP section 6 assigns no ADR. The package does not depend on `backend.adjuster..` either: `adjuster` depends on `fraud` (it is offered the search tool), so a back-reference would be a package cycle; `FraudCheck` therefore declares its own identity map (D7) instead of reusing the private one of `AdjusterChat`. Rejected: putting it into `rag` (that package is the policy wording; the fraud check is its own capability).

**D2 - Corpus: one Markdown file per bulletin with a hand-parsed header, read by one function.** `corpus/sighting-bulletins/*.md`: lines `key: value` (`id`, `observedAt` ISO UTC, `place`), a blank line, then the text. The kaiju class is part of the text ("a class 5 kaiju ..."), not of the header and not stored as metadata: nothing in this change filters or cites by class, so a header field would exist only for the corpus test (rejected: `kaijuClass` as metadata and on the hit; a later change can add it). Seven bulletins, ids `SB-101`..`SB-107`, every text contains "kaiju" and states its class: `SB-101` HARBOUR 11-18 09:05Z, `SB-102` SALTMARSH 11-18 14:45Z ("about 40 km up the coast from the harbour"), `SB-103` SALTMARSH 11-18 15:10Z, `SB-104` HILLTOP 11-18 16:20Z (class 1), `SB-105` HARBOUR 11-19 07:30Z, `SB-106` OLD_TOWN 11-16 09:30Z (class 5), `SB-107` RIVERSIDE 11-17 18:10Z (class 1). One `internal` API in `fraud` serves ingestion and the corpus test, so the test never duplicates the parser: `internal data class SightingBulletin(id, observedAt: Instant, place, text)`, `internal fun parseSightingBulletin(fileName: String, content: String): SightingBulletin` (pure; a missing or unparseable `id`, `observedAt` or `place` throws an exception naming `fileName`, via `checkNotNull`/`requireNotNull` with a message) and `internal fun readSightingBulletins(): List<SightingBulletin>` (all classpath files through `PathMatchingResourcePatternResolver`, like `PolicyWordingIngestion`). A bulletin is short, so no splitter. Rejected: `MarkdownDocumentReader` (no front matter; its metadata cannot carry a time and place per file) and a YAML library (one more dependency for three keys).

**D3 - Time is stored as epoch seconds (`observedAtEpochSecond`, a number).** The pgvector filter converter renders a jsonpath that compares strings, and `AbstractFilterExpressionConverter.normalizeDateString` rewrites an ISO date string to a `Date` printed in millisecond form (`yyyy-MM-dd'T'HH:mm:ss[.SSS]'Z'`, so `...ss.000Z`), so a stored `"2026-11-18T15:00:00Z"` is not `<=` the bound `"2026-11-18T15:00:00.000Z"` (verified on PostgreSQL 18: `Z` sorts after `.`). A number compares numerically and the tool builds the filter with `gte`/`lte` on `from.epochSecond` and `to.epochSecond`. The hit's `observedAt` is derived with `Instant.ofEpochSecond`. Pgvector returns small numbers as `Integer`, so read it as `(value as Number).toLong()`. Rejected: ISO strings in the converter's exact `.SSS` form (works, but couples ingestion to a private formatting detail; the inclusive-bound scenario would be the only guard).

**D4 - `place` is a free string, `SALTMARSH` is the neighbouring town.** Values are the `District` names and `SALTMARSH`, matched exactly with `eq`. The tool description lists them; a blank place is treated as absent. `District` stays the claim-domain enum without the town (the glossary: a neighbouring town for alibis). Rejected: adding `SALTMARSH` to `District` (no claim can happen there) and case-insensitive matching (more code; the description names the exact values).

**D5 - Query rewriting is the model's job.** The model writes the `query` argument and the tool description says to search again, rephrased or at another place, when nothing useful comes back. The 4711 scenario then needs two retrievals: first the claimed place (empty), then the neighbouring town. Rejected: `RewriteQueryTransformer` (a hidden extra model call per retrieval, each using a step of the scripted fake; the agentic behaviour is the point of the demo).

**D6 - The search tool is a `@Component` with one `@Tool` method, no `ToolContext`.** `searchSightingBulletins(query, from: Instant, to: Instant, place: String?)` returns `List<SightingBulletinHit>(bulletinId, place, observedAt, text)`, at most five, filter built with `FilterExpressionBuilder` (`eq corpus`, `gte`, `lte`, optional `eq place`; values go through the builder, never into filter text). `place` needs `@ToolParam(required = false)`: the annotation wins over Kotlin nullability, and a missing argument arrives as `null` (Kotlin defaults are not applied). The format key is stripped from the generated schema, so the time format is written into the descriptions. A `ToolContext` parameter would fail on an empty context and the tool needs no identity. The name differs from every core tool name (collision policy of `adjuster-tools`).

**D7 - The verdict comes from a separate blocking `FraudCheck`, not from the adjuster chat.** `entity<T>()` exists only for blocking calls and the adjuster chat streams; a typed event for the desktop would also change ADR-0005. `FraudCheck.assess(claimNumber: Long): FraudCheckResult` (`Assessed(FraudAssessment)` | `Unreadable`, a `JacksonException` is caught like in `ClaimIntake`) uses a private `ChatClient` from the injected builder (ADR-0010 rule) with `prompts/fraud-check-system.md`, the search tool and a read-only view of the core tools: `ToolCallbackProvider { coreTools.toolCallbacks.filter { it.toolDefinition.name() == "getClaim" }.toTypedArray() }` (filtered per request, so the MCP connection stays lazy and `issuePayout` is never offered). It sends `toolContext(actor=adjuster-agent)` from its own private identity map (the same value as in `AdjusterChat`, not shared: D1). It is one blocking `ChatClient` call that runs a tool loop, so the model is called once per loop step (four times in the 4711 scenario). `FraudAssessment(verdict: FraudVerdict, evidence: List<Evidence>, confidence: Double)`, `Evidence(bulletinId, finding)`, `FraudVerdict { CLEAR, FLAGGED, INCONCLUSIVE }`, with `@field:JsonPropertyDescription` hints. Structured output stays prompt-based (the format instructions are appended to the user message of every model call of the loop), as in `claim-intake`. This mirrors the later `fraud-investigator` (read-only tools plus the sightings tool) without `TaskTools`. Rejected: an adjuster tool `checkFraud` (an agent inside a tool is the `subagents` change) and a desktop event (out of scope).

**D8 - Adjuster wiring is three small edits.** `adjusterChatClient.defaultTools(coreTools, sightingBulletinSearch)` (`defaultTools` takes tool objects and providers together); the adjuster prompt gets one bullet about the bulletins; `AdjusterChat.runToolCalls` adds `*ToolCallbacks.from(sightingBulletinSearch)` to the resume options, because the tool loop keeps no state and `DefaultToolCallingManager` throws "No ToolCallback found for tool name" for a callback missing from the options (a `@Tool` `@Component` is not in the `ToolCallbackResolver`). The resume addition is tested: `FakeChatModel` gains `requestTools(vararg Pair<String, String>)` (one `AssistantMessage` carrying several tool calls, about five lines, tested in `FakeChatModelToolsTest`), and the scenario "A search paused together with a payout runs after approval" scripts one reply with the search and `issuePayout`. A paused reply is held whole until the decision (see `AdjusterChat.decide`), so the search runs only on resume and the test fails without the line.

**D9 - Test data constraints.** `FakeEmbeddingModel` is a hashed bag of words and pgvector drops rows at distance exactly 1 (the SQL is `distance < 1 - threshold`, 1.0 at the default), so a bulletin sharing no word with the query would be dropped even when it matches the filter. Every bulletin text and every test query contains "kaiju", and the specs say so: each scenario that calls the tool names a query such as "kaiju sighting". Real embeddings are practically never orthogonal. The corpus is tiny (HNSW candidates are post-filtered; with about 20 rows every row is a candidate), so topK 5 loses nothing here; a much larger corpus would need a larger `ef_search`.

**D10 - Seeds and fakes.** `FakeCoreTools.getClaim` gains `district`, `incidentAt` and `kaijuClass` (the real tool contract) so the 4711 script is realistic. `AdjusterChatTest` only checks `"status":"FILED"`. `FakeChatModel` gains `requestTools` (D8); `requestTool`, `replyJson` and `prompts` stay as they are.

**D11 - Docs.** README section "Fraud check"; ADR-0006 status-line note (the corpus `sighting-bulletin` is in use, ids `sighting-bulletin/<id>`, wording: "the filter converter rewrites ISO date strings to millisecond form, so string comparisons with stored ISO values break at the bounds; time is stored as epoch seconds and compared numerically"); the glossary in ROADMAP.md names `FraudAssessment`, the verdicts and the town `Saltmarsh` ("swap the names freely").

## Test boundaries

| Behaviour | Boundary | Catches | Misses |
|---|---|---|---|
| Corpus content and header parsing | Unit tests on `readSightingBulletins()` (classpath files) and `parseSightingBulletin(fileName, content)` (malformed text) | the 4711 contradiction exists, no harbour bulletin in the window, fields complete, a malformed file is rejected with its name | embedding and storage |
| Ingestion (metadata, ids, idempotence, failing embedding) | Service `SightingBulletinIngestion` with real pgvector and `FakeEmbeddingModel` (shared `@IntegrationTest` context), failure with a throwing embedding model like `PolicyWordingIngestionTest` | stored rows and metadata, upsert replace-by-id, nothing written on failure | real embeddings |
| Time and place filters, inclusive bounds, corpus isolation | Service `SightingBulletinSearch.searchSightingBulletins` against pgvector; the isolation test upserts a temporary `policy-wording` row that has an `observedAtEpochSecond` in the window and "kaiju" in its text (pattern: `FOREIGN_ID` in `PolicyWordingRetrievalTest`, deleted in `finally`), so only the `eq corpus` filter can keep it out | the generated jsonpath over real JSON metadata, number comparison, the place filter, the corpus filter | whether a real model chooses good arguments |
| Tool definition (required arguments, descriptions) | `ToolCallbacks.from(search)` schema | `required = false` reaching the schema | model behaviour |
| Agent loop, verdict, tool restriction, identity, format instructions | Service `FraudCheck.assess` with `FakeChatModel` + `FakeCoreTools` + real pgvector | two retrievals reaching the model as tool results (the empty result in the third prompt, the `SB-102` result in the fourth, exactly two search responses), `issuePayout` not offered, unreadable reply, prompt contents, format instructions in the last user message of every prompt | real model quality (the `evaluation` change) |
| Adjuster offered the search; claimant not; resume after a payout decision | `POST /chat` and the decision endpoint over the real socket like `AdjusterChatTest` and `AdjusterConfirmationTest`, with `FakeChatModel.requestTools` | wiring on the adjuster client, prompt mention, the callback in the resume options | real model behaviour |
| Package dependencies | ArchUnit | `fraud` free of the chat layer, the protocol, the adjuster package (no cycle) and Exposed | - |

## Risks / Trade-offs

- A hand-parsed header is a tiny format: a malformed file fails startup with the file name in the message (fail fast), which is the point for a fixed demo corpus.
- Prompt-based structured output can fail on a real model; that is the `Unreadable` result, as in `claim-intake`.
- Retrieval quality with real `nomic-embed-text` is not tested; the filters, not the ranking, carry the 4711 scenario.
