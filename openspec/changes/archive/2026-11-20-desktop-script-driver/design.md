# Design

## Context

See proposal.md for motivation. Observed state:

- All screen behaviour lives in `ChatViewModel` (`send`, `prepareClaim`, `confirmClaim`, `decide`, `selectPersona`, `newConversation`, `open`) over a `StateFlow<ChatState>`. `App` builds the view model itself (`remember(chatApi)`) and holds the enablement rules inline (`canSend = !sending && pendingConfirmation == null`, `canConfirm = canSend && message === messages.last()`). The input text is local Compose state (`InputRow`), which nothing outside the composable can fill.
- `main.kt` creates one `HttpChatApi` and a Compose `Window`. The desktop talks only to the backend (ADR-0003, ADR-0005); it has no database access and must not get any.
- `core-mcp` owns the `core` database. The scenario fixtures come from Flyway migrations, so a demo that pays claim 4711 cannot be repeated. Tests of `core-mcp` share one container and assert exact counts over rows no test writes (ADR-0004, "Module `core-mcp`").
- There is no `scripts/` directory yet.

## Goals / Non-Goals

**Goals:** one way for a script and an agent to press the app's controls **visibly** (the demo is shared live: the audience sees the input fill, the control light up, the screen change), wait for answers and read the screen; repeatable demo data; testable without a real backend, model or database for the desktop part.

**Non-Goals:** OS-level mouse and keyboard events, a drawn mouse pointer, opening the persona drop-down list, screenshots, assertions inside scripts, Windows support for the CLI script, authentication of the control endpoint, seeding the `backend` database.

## Decisions

### 1. A control endpoint inside the desktop app, pressing the screen's own controls

`desktop.control` holds a tiny HTTP server (JDK `com.sun.net.httpserver`, no new dependency) bound to `127.0.0.1`, started by `main` only when `DESKTOP_CONTROL_PORT` is a valid port. One route, `POST /command`, body = one command line. Answers are plain text; the status carries the outcome: 200 ok, 400 bad line, 403 `Origin` present, 405 other method, 408 wait timed out, 409 control not usable, 422 the awaited reply ended in an error. `state` answers JSON (one `@Serializable` snapshot type that embeds the existing `chat-protocol` types for cards, confirmation, todos and conversation summaries instead of duplicating them).

The commands run the same `ChatViewModel` functions the controls' `onClick` lambdas run (each lambda is a one-liner to one view-model function), so the backend sees byte-for-byte the same requests, and they make the effect visible as in decision 2. The "is this control usable" rules move from `App` into derived properties of `ChatState` (`canSend`, `canConfirmClaim`, `canDecide`, ...); `App` and the control use them, and a Compose test asserts the screen and the snapshot agree. `main` creates the `ChatViewModel` and passes it to `App` (an overload keeps `App(chatApi)` for the existing tests).

Rejected: **driving the Compose semantics tree like `ComposeUiTest`** (no public API to reach the semantics owner of a running window, so it would need internal API that breaks with Compose upgrades); **OS-level automation** (`java.awt.Robot`, AppleScript: needs accessibility permission and window focus, depends on pixel positions and on the presenter not touching the mouse, flaky, not reproducible for an agent); **a separate CLI module with its own JVM** (slow start, a new module and shared types for no gain); **always-on endpoint** (opens a port in every normal run).

### 2. Visible effects: typing into the real field, a highlight before each click

- **Input text moves into `ChatState`** (`input`, `ChatViewModel.setInput`, and `submitInput()` which sends the input and clears it; Send and Enter call it). The field is bound to `state.input`, so a user's typing and the control's typing are the same state, and the field, not a hidden call, shows the text. `send "<text>"` clears the input, then calls `setInput(text.take(i))` for each `i` with `delay(typingSpeed)` (default 40 ms, `typing-speed <dur>` changes it, `send --instant` sets all at once), then presses Send.
- **Press feedback is one small holder.** `PressFeedback` holds `StateFlow<PressTarget?>` (`Input`, `Send`, `PrepareClaim`, `ConfirmClaim`, `Approve`, `Deny`, `NewConversation`, `Persona`, `Conversation(id)`) and `suspend fun press(target, hold) { set; delay(hold); clear }`. `App` takes it as a parameter (default: a private one, so existing tests are unchanged) and each controllable control gets `Modifier.pressFeedback(feedback, target)`: while it is the target it draws a 2 dp accent outline and sets `stateDescription = "pressed"` in its semantics, which is also how tests assert it. A command is `press(target, highlightTime)` followed by the same call the `onClick` makes; highlight time default 300 ms, `highlight <dur>` changes it, `0ms` skips the pause. The state snapshot reports `pressed` and `input`.
- **Persona**: the switch is highlighted and its label changes; the drop-down list is not opened (follow-up).
- **Why this and not the alternatives:** it is the lightest way to be visible without leaving Compose: no new dependency, one state holder, one modifier, no OS permission, and it works when the window is not focused. Rejected: **`Robot` key and mouse events** (focus, permission, layout-dependent, collides with the presenter's own mouse); **Compose test APIs (`performTextInput`, `performClick`) in production** (test-only, need a test scene); **a simulated mouse pointer overlay** (looks nice, needs coordinates of every control; a follow-up on top of `PressFeedback`); **invoking the view model silently** (the first version of this plan: invisible, fails the live-demo requirement).
- **Same code path:** the parity tests assert the visible effect (see Test boundaries); a click lambda and a command that drift apart would show up there.

### 3. Commands are started, not awaited; waiting is its own command

An action command (`send`, `approve`, ...) returns when the click has happened (typing and highlight done, the view model has accepted it: `sending` is true or the effect is visible) and never waits for the answer: an agent can inspect `state` mid-stream, and `wait-idle` is the one place with a timeout. Action commands (typing and highlighting included) are executed under one mutex, so `send` then `wait-idle` cannot race (`wait-idle` sees `sending` true) and two actions never overlap their highlights. `wait-idle` suspends on the `StateFlow` until `!sending`, then reports `idle` or `idle: confirmation pending (<tool>)` (both success: a pending confirmation is a normal pause of the demo) from the state. A reply that ended in an error fails the wait (422, body `error: <msg>`) and so does a timeout (408): a script or an agent run must stop where the demo broke, and the CLI maps both to exit code 1, so `kaiju-ctl run` stops at that line. `state` and `reply` still show the partial text and the error afterwards. `sleep` is `delay`. `wait-idle`, `sleep`, `state` and `reply` do not take the mutex (a `state` during a wait or while typing answers at once).

Rejected: **blocking `send` until done** (hides intermediate states, ties one HTTP call to a minutes-long model call); **fixed sleeps only** (flaky, slow); **polling `state` in the CLI** (the server already has the flow).

### 4. A not-usable control is a refusal (409), never a silent no-op

The view model ignores actions silently (spec `desktop-chat`). For a script that would hide a broken demo, so the control checks the shared enablement first, before typing or highlighting anything, and answers 409 with the reason. Mirrors what a user sees: a disabled button.

### 5. One parser in a shared library module `control-protocol`

The script and command syntax (tokenising, `\"`/`\\` escapes, durations, the command set, `render(command)` back into a line, `parseScript(text)` with line numbers and the client-side `seed` line) and the state snapshot type live in a new library module `control-protocol` (no runtime, depends on `chat-protocol` for the card, confirmation, todo and conversation types), used by `desktop` and `cli`, like `chat-protocol` (ADR-0005 pattern). The parser first written in `desktop.control` (tasks 2.1, 4.2) moves there (task 6.1) with `ide move-file`.

Why: the CLI builds typed commands from Clikt arguments and renders them through the same `render` the parser inverts, so quoting cannot drift; `demo start` and `demo run` validate the whole script before the first line runs (a typo on line 12 must not surface in front of an audience); `kaiju state` decodes the same snapshot type the app encodes.

Rejected: **parser stays in `desktop`, the CLI forwards lines blindly** (a syntax error is found only when its line is reached, and the CLI re-implements quoting); **`cli` depends on `desktop`** (drags Compose into the CLI jar); **a `/validate` endpoint on the app** (needs the app running just to check a file); **YAML/JSON scripts** (an agent would learn a schema for what is one command per line); **a `/run` endpoint that executes a whole file** (no place for `seed`, one long HTTP call, no per-line progress).

### 6. The `kaiju` command line: a Kotlin module, one executable file

- **Module `cli`** with the `demo.kotlin-jvm` convention plugin, **Clikt** for the commands (Kotlin-first, nested subcommands, generated `--help` per command, typed arguments and choices), kotlinx.serialization, coroutines, the JDK `HttpClient`. Each direct command is a Clikt subcommand that builds a `Command`, `render`s it and POSTs it to `KAIJU_CONTROL_URL` (default `http://127.0.0.1:8765`); a small `ControlClient` maps status to result (200 ok, 400/409/422/408 failed -> exit 1, connection refused -> exit 2). Rejected: **picocli** (annotation and reflection based, a Java style in Kotlin, more native-image metadata), **kotlinx-cli** (stalled, no generated per-command help worth having), **hand-rolled `args` parsing** (help text per command by hand).
- **`state`** prints a readable summary from the decoded snapshot, `--json` the body untouched.
- **One native executable, no JDK at runtime.** The `org.graalvm.buildtools.native` Gradle plugin compiles the `cli` module into a native image (`:cli:nativeCompile`, output `cli/build/native/nativeCompile/kaiju`); `:cli:installKaiju` depends on it and copies the file to `./kaiju` in the project root, executable bit set. `/kaiju` and `.kaiju/` are git-ignored. The binary holds everything (no JDK, no jar, no stub), starts in about 20 ms, and is what the daemon relaunches.
  - **Toolchain, for the native compile only:** the module's `graalvmNative { binaries.main { javaLauncher = javaToolchains.launcherFor { languageVersion = 25; vendor = GRAAL_VM; nativeImageCapable = true } } }`. The settings already apply the foojay toolchain resolver, so Gradle downloads a GraalVM 25 JDK on first use; the fallback when that is not possible (offline, resolver has no build for the platform) is a documented install (`sdk install java 25-graalce` or any GraalVM 25 with `native-image`) found through `JAVA_HOME`/`GRAALVM_HOME`. Everything else (compile, tests, `check`) uses the normal JDK 25 toolchain, so a developer without GraalVM can build and test all modules.
  - **Native-image friendliness:** Clikt (no reflection), kotlinx.serialization with the compiler plugin (generated serializers, no reflection), coroutines, the JDK `HttpClient` and `com.sun.net.httpserver` (both supported) and `FileChannel` locks are all fine; no Ktor, no Jackson, no Spring in this module. The bundled SQL needs one resource include (`resources { autodetect() }` or `-H:IncludeResources=demo-seed/.*\.sql`), and the plugin's reachability-metadata repository stays on for the libraries. Anything that still fails shows up in the native smoke test (below) and is fixed with a `reachability-metadata.json` in `cli/src/main/resources/META-INF/native-image/`.
  - **Rejected: a fat jar with a shell launcher stub** (the first version of this plan): needs a JDK 25 on every machine that runs it and about half a second of JVM start per command. **Backup if the native compile turns out unworkable** (for example a library needs metadata that cannot be written): a self-extracting single file, a shell stub followed by a `jlink` runtime image (`java.base`, `java.net.http`, `jdk.httpserver` ...) and the jar, extracted on the first run to a versioned cache directory (`.kaiju/runtime-<build>/`) and run from there. Trade-offs: native is about 20 ms to start and builds slowly (minutes, GBs of RAM) and needs a GraalVM to build; jlink uses standard JDK tooling and builds fast, but the file is larger (about 40 MB) and the first run extracts, and a stub is POSIX shell only.
- **Version identity**: the SHA-256 of the executable file (its path from `ProcessHandle.current().info().command()`), computed once at start; in JVM tests it is injected.
- **Seeding** (decision 8) is a CLI command.
- **Version identity**: the SHA-256 of the executable file, computed once at start (`java.class.path` is the file when run with `-jar`); in tests it is injected.

### 7. The demo daemon: owns the running demo only

- **Why a daemon at all:** a demo that runs for minutes and can be stepped, inspected and stopped from separate command invocations needs one process that outlives them. It holds `{file, lines, current line, state, last error}` and nothing else; every control line goes to the desktop endpoint, so the desktop stays the only source of truth for the screen (spec scenario "Daemon replaced mid-demo"). Direct commands and `state` never touch it.
- **Same executable, detached.** `DaemonLauncher` starts `<this executable> daemon` (its path from `ProcessHandle.current().info().command()`) with output to `.kaiju/daemon.log` and no inherited stdio; it survives the CLI. When the CLI runs on the JVM (for example `:cli:run`), where that path is `java`, the launcher refuses with "build the executable with `:cli:installKaiju`" (exit 3). A start timeout (default 10 s) gives exit code 3 with the log path.
- **Single instance:** (1) the daemon takes an exclusive `FileChannel` lock on `.kaiju/daemon.lock` for its lifetime and exits at once if it cannot; (2) it writes `.kaiju/daemon.json` `{pid, port, build}` after binding; (3) a CLI that needs the daemon holds a short lock on `.kaiju/start.lock` while it checks `daemon.json` (stale = no answer on `GET /health`), launches and waits for health, so two simultaneous CLIs launch one daemon.
- **Version handshake:** `GET /health` answers `{build, pid}`. A different build -> `POST /shutdown`, wait for the lock to free, launch its own. The running demo is lost; `status` says so.
- **Idle exit:** default 5 minutes (`KAIJU_DAEMON_IDLE`, a duration), counted from the last request or the end of the last demo; a demo in state `running` or `waiting-step` counts as active. 5 minutes covers a pause in a talk and still frees the process well before the next day.
- **Transport:** loopback HTTP (JDK `HttpServer`) on an ephemeral port recorded in `daemon.json`; JSON bodies; `Origin` refused (403). Paths: `GET /health`, `POST /shutdown`, `POST /demo/start` (`{name, lines, step, controlUrl}`: the CLI reads the file, so relative paths and the daemon's working directory do not matter), `POST /demo/next` (answers when the line has finished: the status and output of that line), `GET /demo/status`, `POST /demo/stop`. Rejected: **a unix domain socket** (path-length limit on macOS, the JDK `HttpClient` cannot speak it, so a second client stack, and no gain over loopback for a local-only tool), **a TCP port fixed in config** (collides), **no daemon, `demo run` only** (cannot be stepped or asked from another invocation, which the agent-driven presentation needs).
- **Runner:** a `DemoRunner` (control client + `SeedRunner` + the parsed script) is the one piece that executes lines. The daemon runs it in a coroutine, `demo run` runs it in the CLI process and prints progress. It stops at the first failure (any non-200 control answer, an unreachable app, a failed seed). Step mode suspends before each command line until `next`.
- **Failure of the whole idea is cheap:** killing the daemon loses only the demo's position.

### 8. Seeding: SQL owned by `core-mcp`, bundled into the executable, applied by the CLI

`core-mcp/src/main/resources/demo-seed/reset.sql` and `desk-queue.sql` stay plain idempotent SQL (delete-then-insert for the rows a set owns, `setval` after explicit ids as the existing seed migration does; no psql meta-commands or `$$` blocks, so a JDBC script runner and `psql` agree). The `cli` build copies that directory into its resources (`processResources { from(<core-mcp>/src/main/resources/demo-seed) { into("demo-seed") } }`): a file-level build input, so the CLI has **no dependency on core-mcp code**, the files stay authored and tested by `core-mcp`, and `./kaiju` works from any directory. A `SeedSet` enum lists `reset` and `desk-queue`; a test compares it with the bundled files so a new file cannot be forgotten.

`SeedRunner` is a port with one method (apply this SQL); the real adapter runs `docker compose -f <compose.yaml> exec -T postgres psql -v ON_ERROR_STOP=1 -U demo -d core` with the SQL on standard input (`compose.yaml` = next to the executable, else `KAIJU_COMPOSE_FILE`), and maps "service not running" to the exit-1 message. Tests use a fake `SeedRunner` that records the SQL. The files live in `core-mcp` because it owns the schema and the fixtures; the CLI is dev tooling like Flyway, not a runtime path from `backend` or `desktop` into `core` (ADR-0003 stays intact). Seeds avoid the analytics districts (`HARBOUR`, `OLD_TOWN`, `HILLTOP`) and the sandbox policy `KP-9000`, and `reset` leaves the sandbox claims alone, so the shared test database keeps its invariants.

Why `reset` exists: payouts and status changes are one-way, so without a reset a demo can be run once per database.

Rejected: **reading the SQL from the repository path at run time** (breaks when `./kaiju` runs elsewhere or the checkout moves, and couples the CLI to the source layout); **depending on `:core-mcp`** (Spring Boot on the CLI classpath); **seeding through MCP tools** (cannot restore `FILED` or remove a payout; needs an OAuth handshake); **an admin endpoint in `core-mcp`** (new scope, auth-server changes, a write endpoint on a security-demo service); **more Flyway migrations** (applied everywhere, always, and tests would see them); **a `seed` command inside the desktop** (breaks data ownership).

### 9. ADR

ADR-0011 "Demo driver and seeding" records decisions 1, 2, 5, 6, 7, 8 and 10: the control endpoint and its env var, the two new modules (`control-protocol` as a shared library module, `cli` as a runtime artifact; ADR-0001 requires an ADR for both), the executable, the daemon (lifecycle, lock, transport, handshake, idle default), the seed location and who may apply it. ADR-0004 gets an addendum for the desktop control, CLI and daemon tests, ADR-0003 one line that the seed SQL for `core` is owned by `core-mcp` and applied only by `./kaiju seed`.

### 10. Security stance

The endpoint can approve a payout, so it is loopback-only, off by default, refuses requests with an `Origin` header (a web page in the user's browser cannot POST commands: browsers send `Origin` on cross-origin POSTs) and answers no other method. The daemon has the same posture (loopback, `Origin` refused) and can start a demo that drives the app, so it is no wider than the endpoint it forwards to. No token: the repository's local endpoints have none (ADR-0009: "the backend's own endpoints have no security") and the real payout control stays with the backend's confirmation flow, which the control only presses like a user. Any local process of the same user can drive the app; that is the feature.

Fakes over mocks; the existing `FakeChatApi` (records requests, `Channel`-backed replies for in-flight states) is the only test double.

The JVM tests (all rows except the native smoke test) run in `test` and so in `check`. The native smoke test is tagged `native`, excluded from `test`, and runs as the separate task `:cli:nativeSmokeTest` (depends on `nativeCompile`, takes the binary path as a system property); it is **not wired into `check`**: a native compile takes minutes and several GB of RAM and needs GraalVM, and `./gradlew check` must keep working with the JDK 25 toolchain alone (the same separation ADR-0004 already makes for the `evaluate` task). Task 8.2 runs it, and a failing native smoke test is a failed change.

No ArchUnit rule is planned: the JDK server is the only transport and the only dependency, which the build file shows.

## Risks / Trade-offs

- [Reset deletes rows a test relies on] -> it spares `KP-9000` claims and the history; the task runs the whole `:core-mcp:test` after the seed test, in both orders of test classes.
- [`seed` applied against the wrong database] -> the script always targets database `core` of the compose service `postgres`; no connection string is configurable.
- [Control and click disagree] -> shared `ChatState` rules plus the parity test.
- [The presenter types or clicks while a command types] -> both write the same `input` state, so text can interleave; commands refuse (409) when an answer streams but not when the user is typing. Accepted: during a scripted demo the presenter does not touch the keyboard.
- [Highlight and typing slow every scripted step] -> `typing-speed 0ms`, `highlight 0ms` and `send --instant` for agent runs; defaults (40 ms per character, 300 ms highlight) are tuned for a live audience.
- [The field shows no caret while typing, so it looks less real] -> the input is outlined while typed into; a caret is a follow-up if it looks odd.
- [Native compile is slow and needs GraalVM] -> only `installKaiju`/`nativeSmokeTest` need it, `check` does not; the jlink self-extracting file is the recorded backup.
- [A library fails in the native image] -> the native smoke test finds it; reachability metadata goes into `cli/src/main/resources/META-INF/native-image/`.
- [`wait-idle` default 180 s is too short for an adjuster run with subagents] -> the timeout is an argument; scripts say `wait-idle 5m`.

## Resolved questions

All answered by the user; none is open.

- "New checks" means `new-conversation` followed by `send` (for example an adjuster conversation that sends "Run a fraud check on claim 4711"); there is no dedicated check command.
- Seed scope is the `core` database only (`reset`, `desk-queue`). Clearing the backend's stored conversations stays a follow-up.
- An error reply fails `wait-idle` (422, exit code 1); a pending confirmation does not.
- Visible typing and press feedback are in scope (decision 2). The defaults (40 ms per character, 300 ms highlight, `wait-idle` 180 s) and the 16-task plan are approved.
- Follow-ups, not part of this change: screenshots for agents, assertion commands (`expect-reply`), a drawn mouse pointer, opening the persona drop-down, a visible caret.
