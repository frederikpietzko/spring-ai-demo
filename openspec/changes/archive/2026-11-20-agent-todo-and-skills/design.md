## Context

- The adjuster agent (`backend/adjuster`) streams `chatResponse()` from `adjusterChatClient` (core MCP tools as default tools) and turns chunks into `TextDelta` or a terminal `ConfirmationRequest`. `decide` resumes a paused reply with `ToolCallingManager.executeToolCalls` and then streams a new turn (stateless, ADR-0005 addendum). `ChatController.withTerminalEvent` adds `Done` only after `TextDelta` or nothing.
- `spring-ai-agent-utils` 0.13.0 (Maven Central, Apache-2.0, no auto-configuration) is built against Spring AI 2.0.1. Its `TodoWriteTool` and `SkillsTool` are byte-identical on `main` (0.14.0-SNAPSHOT, Spring AI 2.1.0-SNAPSHOT); every Spring AI method they call (`FunctionToolCallback.builder(...).description().inputType().build()`, `@Tool`, `@ToolParam`) exists with the same signature in 2.1.0-RC2 (checked with `javap` and the sources before planning). Runtime compatibility is proven by the first backend test (task 3).
- Verified Spring AI 2.1.0-RC2 behaviour this plan relies on (re-check what you depend on): request `.tools(...)` is appended to `defaultTools(...)`; tool-call chunks never reach `chatResponse()` (the `ToolCallingAdvisor` filters them), so a todo update cannot be read from the stream; tools run on `boundedElastic`; an invalid tool call throws `IllegalArgumentException`, which becomes the tool result text (default `throw-exception-on-error=false`); on resume every call of the paused reply needs a decision and every allowed call needs its callback in the prompt options; tool results pass through `DefaultToolCallResultConverter`, so a Markdown result reaches the model JSON-quoted.
- `TodoWriteTool.todoEventHandler` gets only the `Todos`: no tool context, no conversation id.

## Goals / Non-Goals

**Goals:** the adjuster plans with a todo list the user sees update live; it loads two skills on demand; one obvious class per concept; offline tests with the existing fakes.

**Non-Goals:** subagents, claimant todos or skills, persisting todos, keeping the list across a payout decision, filesystem skills, the other agent-utils tools.

## Decisions

**D1 - Depend on `spring-ai-agent-utils:0.13.0`, do not copy (roadmap R2, ADR-0007).** Explicit version in `libs.versions.toml` (the Spring AI BOM does not manage it); `exclude(group = "com.vladsch.flexmark")` because only `SmartWebFetchTool` uses it. Rejected: copying the two classes (no 2.1-specific change exists on `main`, and the demo is about using the library); pinning `0.14.0-SNAPSHOT` (not reproducible).

**D2 - One `TodoWriteTool` per request, its handler feeds a `channelFlow`.** `AdjusterChat.turn(conversation)` keeps its one argument and becomes a `channelFlow` that builds its own `TodoWriteTool` for the turn: `TodoWriteTool.builder().todoEventHandler { trySend(it.toTodoUpdate()).getOrThrow() }`, adds it with `.tools(todoWrite)` and collects the model stream as before, sending text and pause events; `.buffer(Channel.UNLIMITED)` so `trySend` never fails while the stream is open. `Todos.toTodoUpdate()` is one small extension in `adjuster/TodoUpdates.kt`. Rejected: one singleton tool with a sink in the `ToolContext` (the handler gets no context, and the tool context is forwarded to `core-mcp` as MCP `_meta`); deriving updates from the streamed tool calls (filtered out).

**D3 - `TodoUpdate(todos: List<TodoItem>)` carries the whole list.** `TodoItem(content, status, activeForm)`, `TodoStatus { PENDING, IN_PROGRESS, COMPLETED }`, wire name `todo-update`, non-terminal. The library sends the whole list on every call, so the event means "replace". Rejected: per-item deltas (more state on both sides for no gain).

**D4 - `Done` after every reply that did not end itself.** `withTerminalEvent` becomes `if (last?.isTerminal != true) emit(Done)`. A reply whose last event is a `TodoUpdate` (empty final text) otherwise ends without a terminal event and the desktop shows "connection closed". Rejected: special-casing `TodoUpdate` in the controller (the next non-terminal event would repeat the bug).

**D5 - Skills: one `Skill` callback, declared once as a qualified bean.** `AdjusterConfiguration` declares `@Bean fun adjusterSkills(@Value("classpath:skills") skills: Resource): ToolCallback = SkillsTool.builder().addSkillsResource(skills).build()` (a `ClassPathResource`, so the library scans `classpath*:skills/**/SKILL.md`, jars included). The bean is injected with `@Qualifier("adjusterSkills")` into the `adjusterChatClient` bean method (`defaultTools(coreTools, adjusterSkills)`) and into `AdjusterChat`, which puts the same callback into the resume options (D7). Frontmatter holds only `name` and `description` on single lines (the parser has no multi-line YAML and lists every key in the tool description). The `kaiju-classification` and `damage-estimation` bodies reuse the glossary (class 1-5) and the `DamageCategory`/`District` vocabulary; they contain no secret-looking `key: value` lines (secrets scan). Why a bean is safe: the claimant client is only offered what it is given, and the bean can reach a model only through `ToolCallbackResolver` name resolution, which is off by default (`DefaultToolCallingManager.DEFAULT_RESOLUTION_FALLBACK_ENABLED = false`, spring-ai-model 2.1.0-RC2), so a model that was not offered `Skill` cannot call it. Rejected: building the callback inside the `adjusterChatClient` bean method and keeping "the object a constructor argument of `AdjusterChat`" (impossible without a bean, so `AdjusterChat` could not put it into the resume options), and a second `SkillsTool` instance in `AdjusterChat` (two scans of the same resource).

**D6 - "Names and descriptions up front" means the `Skill` tool definition.** `SkillsTool` puts them in the tool description (`<available_skills>` block), not the system prompt; the body arrives only as the tool result. The roadmap test is asserted on what the model sees up front (system message plus tool definitions) versus the tool result. **Deviation from `ROADMAP.md`** (entry `agent-todo-and-skills`, Tests: "Only skill names and descriptions sit in the system prompt"): the system message carries none of them, the `Skill` tool definition does. It is reported as a decision for the owner's review, written into ADR-0007 and the roadmap line is reworded in task 6.2. Rejected: rendering the skill list into `adjuster-system.md` ourselves (duplicates the library and needs template parameters). The adjuster prompt gains one line: plan multi-step work with `TodoWrite`, load a skill with `Skill` when its description fits.

**D7 - Resume handles todo and skill calls; deny stops only what waits for a decision.** `decide` becomes a `channelFlow` too. It builds a second `TodoWriteTool` (per decision) only for `runToolCalls`, whose handler feeds the same channel; the following model turn is `turn(conversation)`, which builds its own tool as in D2, and `decide` forwards its events. `runToolCalls` builds the options with the core tools, `ToolCallbacks.from(todoWrite)` and the `adjusterSkills` callback, and approves or denies only the keys in `ToolCallDecisions.awaitingDecision(reply)`; every other key is `allow`ed. This changes the existing deny rule ("deny runs none of the paused calls", capability `adjuster-tools`, ADR-0005 addendum): deny now stops the calls that wait for a decision, and the other calls of the same reply (`TodoWrite`, `getClaim`, `Skill`) run normally. The change therefore modifies `adjuster-tools` (delta spec), corrects the ADR-0005 addendum (task 6.1) and the `decide` KDoc (task 4.1). Without this, a paused batch of `TodoWrite` plus `issuePayout` fails on approve (no callback in the prompt) and hands the payout denial text to the todo call on deny. `FakeChatModel.requestTools(vararg)` scripts one reply with several calls for the test. Rejected: leaving the path as is (a real parallel-call bug).

**D8 - Desktop panel.** `ChatState.todos: List<TodoItem> = []`; `ChatViewModel` replaces it on `TodoUpdate` and clears it on `newConversation`, `open(conversation)` and `selectPersona` (the list belongs to the conversation on screen, so a transcript loaded from the history never shows another conversation's todos; `open` clears it in the same `copy` that sets the messages, after its existing guards); `App` shows a `TodoPanel` (fixed width, right of the conversation column) only when the list is not empty: `activeForm` for the `IN_PROGRESS` item, `content` for the others, with a text marker per status (`[ ]`, `[>]`, `[x]`). Rejected: a collapsible panel and animations (demo).

## Test boundaries

| Behaviour | Boundary | Catches / misses |
| --- | --- | --- |
| `TodoUpdate` JSON, terminal-ness | `chat-protocol` unit test | wire names and the exhaustive `isTerminal`; not the transport |
| Todo writes become SSE events, invalid list, `Done` after a todo-only tail | HTTP `POST /chat` in the shared `@IntegrationTest` context with `FakeChatModel` and the real `TodoWriteTool` (`sseEvents(body)`) | the whole path model -> tool -> handler -> controller -> SSE and library compatibility with 2.1.0-RC2; not incremental flushing (ADR-0005 accepted gap) or the ordering of an update against earlier text of the same round |
| Skill names and descriptions up front, body on demand | `fake.prompts[0]` (system message, `Skill` tool definition) and `fake.prompts[1]` (tool response), same context | what the model receives; not what Anthropic does with it |
| Skills load from the classpath | plain unit test with `ClassPathResource("skills")` | resource scanning and frontmatter; fixture skills are not put under `skills/` of the test resources |
| Resume with a mixed batch | HTTP `POST /chat/decisions` after a pause, scripted with `requestTools` | the decide-only-awaiting rule and the todo event after approve; not a real MCP core |
| Todo state and panel | `ChatViewModelTest` with `FakeChatApi`; `AppSemanticsTest` (text of the panel) | state and visible text; not layout (render test untouched) |
| Deny and approve apply to the calls that wait for a decision only | HTTP `POST /chat/decisions` after a pause (`requestTools`: `TodoWrite` or `getClaim` next to `issuePayout`), same context | which calls run and which tool response the model gets; not a real MCP core |
| ADR-0007 present | `docs/adr` listing checked in task 6.1 (no automated test, like the other ADR requirements) | presence and the pinned version in the text; not that the text is true |

No ArchUnit rule is added: nothing here changes the package structure or a layer rule.

## Risks / Trade-offs

- A `TodoUpdate` is sent from a tool thread and can overtake text chunks of the same round that `asFlow()` still buffers. It never falls behind later text, a confirmation request or `Done`. The panel is separate from the text, so nothing shows; fake tool rounds carry no text, so tests are deterministic.
- The todo list is lost for the model across a payout decision (stateless resume); the panel keeps the last list until a new update arrives.
- The library's `TodoWrite` description is long (software-development examples, about 2-3k tokens per adjuster request) and cannot be shortened without copying the class. Accepted.
- The `Skill` result starts with `Base directory for this skill: <path>` (a local path leaks to the model). Accepted; hiding it needs our own frontmatter parsing.
- 0.13.0 targets Spring AI 2.0.1 while we run 2.1.0-RC2. The first backend tests (task 3) prove the runtime fit; if a class does not work, the fallback is to copy the one class into `backend` (record as a decision in ADR-0007).
