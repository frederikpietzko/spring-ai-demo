# Design

## Context

`core-mcp` serves six tools and two resources without authentication. The backend has one MCP connection `core` and one provider bean `mcpToolCallbacks`, used by the adjuster; the claimant chat has no MCP tools (claims are filed by `InMemoryClaimFiling`). The adjuster sends `actor=adjuster-agent` in the `ToolContext`; the default converter forwards every context entry as `_meta` and `core-mcp` ignores it today. ADR-0003 reserves `auth-server` (port 9000, package `authserver`). ADR-0007 does not exist in this worktree. A throwaway spike (outside the repo, same BOMs) proved that the plain `mcp-security` modules 0.1.14 work on Spring AI 2.1.0-RC2 / Boot 4.2.0-RC2, so ROADMAP R1's 2.0 fallback is not needed. Every API below was checked against sources in that spike; the implementer re-checks anything not marked as verified.

## Goals / Non-Goals

**Goals:** tokens per persona from a real auth-server; `core-mcp` enforces token, scope and claimant ownership on every tool and resource; tests prove it end to end against the real auth-server.

**Non-Goals:** end-user login, DCR, token propagation from a user, key persistence, giving the claimant chat any core tools (see proposal).

## Decisions

**D1 Pin `mcp-security` 0.1.14, plain modules only.** Catalogue entries `mcp-authorization-server`, `mcp-server-security`, `mcp-client-security` (group `org.springaicommunity`), version `mcpSecurity`. Boot starters `spring-boot-starter-security-oauth2-authorization-server` (auth-server) and `-resource-server` (core-mcp) come from the Boot BOM. Not the `*-spring-boot` modules: built against Boot 4.1, untested here, and the server one builds its decoder eagerly. Upstream says 0.1.x targets Spring AI 2.0, so the combination is verified by us only; ADR-0009 says so. Rejected: pinning Spring AI 2.0 in `core-mcp` and `auth-server` (not needed).

**D2 auth-server: fixed clients in Kotlin, `client_credentials` only.** One `SecurityFilterChain` of `authorizeHttpRequests { anyRequest().authenticated() }` together with `.with(mcpAuthorizationServer()) { dynamicClientRegistration(false) }` (the explicit authorization rule is needed: the community configurer's `init` calls `authorizeHttpRequests` but adds no mapping when DCR is off, and Spring Security 7.2 then fails at startup with "At least one mapping is required"; the token, metadata and JWKS endpoints answer in their own filters before that rule applies). DCR is the OAuth2 endpoint `/oauth2/register` (the configurer defaults `supportDynamicClientRegistration = true` and opens it with `clientRegistrationEndpoint(cr -> cr.openRegistrationAllowed(true))`; read in `mcp-authorization-server` 0.1.14); `/connect/register` is the unrelated OIDC endpoint, so the test posts to `/oauth2/register` and is made red once by flipping the flag to `true`. An `InMemoryRegisteredClientRepository` with the two clients (`CLIENT_SECRET_BASIC`, scopes per the proposal, secret stored as `"{noop}$secret"` built in Kotlin). The issuer is pinned with `spring.security.oauth2.authorizationserver.issuer: ${AUTH_SERVER_URL:http://localhost:9000}` so `iss` never depends on the request's host spelling (`localhost` vs `127.0.0.1` would otherwise give 401 "iss claim is not valid"). Rejected: YAML clients (`{noop}` + literal trips the secrets scan), plain Spring Authorization Server without the community module (works too, but the demo is about `mcp-security`; one `.with(...)` line to remove if it breaks).

**D3 Secrets: environment placeholders with a documented local default, in YAML only.** The one committed default of each secret lives in the module's `application.yaml` as `agents.claimant.secret: ${CLAIMANT_AGENT_SECRET:<local default>}` and `agents.adjuster.secret: ${ADJUSTER_AGENT_SECRET:<local default>}` (auth-server and backend, so two copies of the literal, as for `DB_PASSWORD:demo` today). Kotlin reads them with `@Value("\${agents.claimant.secret}")` without a default and adds `{noop}` itself, so no `{noop}` literal and no second default exists in code. The scanner accepts the literals because both variable names and their literals are added to `SecretScanner.allowedLiterals` next to `DB_PASSWORD=demo`; the demo runs without setup. Tests never use the defaults: they generate UUID secrets and register them as the properties `CLAIMANT_AGENT_SECRET` and `ADJUSTER_AGENT_SECRET` (what the placeholder resolves, as an environment variable would). Rejected: no default (setup friction for a demo), a default in Kotlin (second place, and `{noop}` rule).

**D4 core-mcp is a resource server with a lazy decoder.** `mcpServerOAuth2()` with `authorizationServer(issuerUri)` and `jwtDecoder(<Boot's JwtDecoder bean>)`; always passing the decoder keeps startup from fetching issuer metadata, so `core-mcp` starts without the auth-server. Property `spring.security.oauth2.resourceserver.jwt.issuer-uri: ${AUTH_SERVER_URL:http://localhost:9000}`. All requests need authentication. CSRF is disabled explicitly (`csrf { disable() }`; the endpoint is stateless and bearer-only): Spring Security 7.2 exempts only requests that carry a bearer token from CSRF (`BearerTokenRequestMatcher`), so without this a POST with no `Authorization` header would be rejected by `CsrfFilter` with a 403 and reach the client as 401 only through the unauthenticated `/error` re-dispatch; with it, the 401 comes from the bearer entry point itself. Rejected: eager decoder (core-mcp would not start first).

**D5 Denials are tool errors, per tool, by hand.** One `@Component` in package `coremcp.security` (`CallerAccess`) reads the `Authentication` from the `SecurityContextHolder` (set inside `@McpTool` methods: Spring AI runs sync servlet tools on the request thread, verified) and offers `scopeDenial(scope): String?` and `ownershipDenial(meta, customerId, what): String?`; `null` means allowed. Tools turn a denial into `ToolResults.error(...)`, resources throw `IllegalArgumentException` (the resource callback turns it into an MCP error). The scope check is the first line of each tool, the ownership check follows the lookup. Scopes: `findPolicy` policies:read; `getClaim`, `listClaimsForCustomer` claims:read; `fileClaim`, `updateClaimStatus` claims:write; `issuePayout` payout:write; the two resources have no scope check (a valid token plus, for claimants, ownership; both registered clients hold `claims:read` and `policies:read` anyway, so a scope rule there would add a scenario and no protection in this demo); tools added by `claims-analytics` (if landed first) use `analytics:read` and are adjuster-only, and the implementer secures whatever tool classes exist then. Rejected: `@PreAuthorize` (verified to work, but answers `Access Denied\nAccess Denied`; the domain-error-as-tool-error style gives the model a clean sentence naming the scope), an HTTP-level 403 rule (cannot see the tool name).

**D6 Claimant identity.** The token proves the persona (`sub == "claimant-agent"` makes it a claimant call); `_meta.claimantId` names the customer (a `McpMeta` tool parameter, left out of the tool schema; the JSON number arrives as `Number`). A claimant call without `claimantId` is refused. The backend is the only party that can set it (the model never sees the `ToolContext`; the claimant agent's client secret stays in the backend). Ownership by `Claim.customerId` / `Policy.customerId`; adjuster calls skip it. `updateClaimStatus` additionally refuses claimant calls: its `claims:write` is needed by the claimant for `fileClaim`, and a new scope would leave the fixed five-scope list of ROADMAP/ADR-0009. Rejected: a sixth scope `claims:review`.

**D7 Backend: client registrations in Kotlin, one connection per persona, no Boot security starter.** Adding `spring-boot-starter-security-oauth2-client` would add a default security chain that locks the backend endpoints and `oauth2Login`. Without it `spring.security.oauth2.client.*` is not bound, so `InMemoryClientRegistrationRepository` with the two registrations (token URI `${AUTH_SERVER_URL}/oauth2/token`, no issuer discovery at startup, scopes requested explicitly because SAS grants none otherwise) and an `AuthorizedClientServiceOAuth2AuthorizedClientManager` are beans written in Kotlin. A `McpClientCustomizer<HttpClientStreamableHttpTransport.Builder>` adds `OAuth2ClientCredentialsSyncHttpRequestCustomizer(manager, registrationId)` per connection with `addHttpRequestCustomizer` (the plain `httpRequestCustomizer` is deprecated and clears others). YAML: `spring.ai.mcp.client.toolcallback.enabled: false` (the auto provider would publish both connections' tools under `noPrefix()`, duplicates) and the two connections. `personaTools(clients, connectionName)` builds a `SyncMcpToolCallbackProvider` per persona, with the existing `noPrefix()` generator bean and a `toolContextToMcpMetaConverter` that keeps only `actor` and `claimantId` (the claimant's `conversationId` must not leave the backend). The persona beans are conditional on `spring.ai.mcp.client.enabled` (matchIfMissing) because the shared test context switches the client off. `AdjusterConfiguration` and `AdjusterChat` switch their qualifier to `adjusterCoreTools`; the test fake moves to that bean name. Rejected: the `-spring-boot` client module (DCR/authorization-code, brings web security), one shared connection with a per-call token (the persona must be fixed by the connection, not by the model's turn).

**D8 No chat client uses `claimantCoreTools` yet.** The payout confirmation is global by tool name (`spring.ai.tools.confirmation.tools: issuePayout`); a claimant chat that offered `issuePayout` would pause on a decision it never handles. The claimant connection and provider exist so the per-persona token path is real and tested (stub), and a later change can route claim filing through it. Rejected: wiring `ClaimFiling` to `fileClaim` here (separate behaviour, ADR-0003's note on `InMemoryClaimFiling`, out of this roadmap entry).

**D9 core-mcp tests fork the real auth-server.** A `TestInfrastructure` bean (`AuthServerProcess`) runs `java -cp <auth-server runtime classpath> ...AuthServerApplicationKt` with the test JVM's own `java`, `--server.port=<free port> --server.address=127.0.0.1`, env `AUTH_SERVER_URL=http://127.0.0.1:<port>` and generated UUID secrets, waits for `/.well-known/oauth-authorization-server`, and destroys the process when it receives a `ContextClosedEvent` (the class is an `ApplicationListener<ContextClosedEvent>`, so a unit test delivers that event, built with a plain `GenericApplicationContext`, and the real hook is exercised, not a `close()` call). The classpath comes from a resolvable Gradle configuration `authServerRuntime(project(":auth-server"))`, passed lazily as `-Dauth-server.classpath` through a `CommandLineArgumentProvider` (configuration-cache safe, and an input of the test task). A `DynamicPropertyRegistrar` bean depending on the process sets `spring.security.oauth2.resourceserver.jwt.issuer-uri` (the context cache key stays in `@CoreMcpIntegrationTest`). `McpTestClient` fetches its token with the JDK `HttpClient` and sends it as the `Authorization` header; the default bean is the adjuster (`@Primary`), a second bean is the claimant; `call(..)` gains an optional `meta` map; a helper builds a client for a claimant token with chosen scopes. Rejected: in-process `SpringApplicationBuilder(AuthServerApplication)` (two Boot contexts in one JVM share the DataSource/Flyway/MCP auto-configurations and `application.yaml`, and the SAS auto-configuration replaces the resource server's decoder; needs several excludes and is fragile), a hand-signed JWT (the roadmap demands a real auth-server).

**D10 Architecture rule.** An ArchUnit rule in `core-mcp`: classes with a method annotated `@McpTool` or `@McpResource` must depend on `CallerAccess`. It guards tools added by parallel changes.

## Test boundaries

| Behaviour | Boundary | Catches / misses |
|---|---|---|
| Token endpoint, scopes, secrets, JWKS, issuer | `auth-server` HTTP over a real port (`@SpringBootTest` RANDOM_PORT, one shared context, generated secrets) | Real SAS wiring and the Kotlin clients; misses any resource-server behaviour |
| 401 without token, scope and ownership denials, adjuster works | `core-mcp` through the MCP SDK client (and one raw JDK `HttpClient` POST for the 401) against the running server and the forked auth-server | The whole chain token to tool result; misses behaviour after token expiry or an auth-server restart (accepted) |
| Tool classes secured | ArchUnit in `core-mcp` | Forgotten checks on future tools; not whether the right scope is named |
| Persona registrations, token per connection, `_meta` allowlist, names, lazy start | Backend `ApplicationContextRunner` (as `McpClientWiringTest`) with a JDK `HttpServer` stub for the token endpoint and the core; the converter as a plain function | Config and wiring of the OAuth client; misses a real core and a real auth-server in the backend, and any Boot security auto-configuration (the runner loads only the four MCP and tool auto-configurations; closed by the manual smoke task and the next row) |
| Backend endpoints stay open | Existing shared `@IntegrationTest` (`EndpointsTest`: no `SecurityFilterChain` bean in the full auto-configuration; the existing `/chat` tests already post without a token) | A security starter pulled in by a dependency; misses nothing relevant. `inspect_dependencies` in 5.3 is the second guard |
| `AuthServerProcess` lifecycle | Plain unit test: start, deliver a `ContextClosedEvent`, assert the process exited | The real shutdown hook; misses nothing the shared context does additionally |
| Adjuster chat | Existing shared `@IntegrationTest` with the fake under `adjusterCoreTools` | Qualifier rename; unchanged behaviour |

## Risks / Trade-offs

- **Unsupported combination** (`mcp-security` 0.1.x vs Spring AI 2.1) → pinned, spike-verified, recorded in ADR-0009; the plain-SAS fallback is one line.
- **Auth-server restart** gives a new RSA key, so the backend's cached token fails with 401 until it expires (default 5 minutes) → accepted for a demo, written in ADR-0009.
- **Claimant id is trusted from `_meta`** → fine because only the backend holds the claimant client secret and the model never sees the `ToolContext`; a fixed demo claimant stands in for login (follow-up).
- **Child JVM harness** costs a process start and a free-port race → the port is probed and reused immediately; startup wait has a timeout that fails the context with the child's output.
- **Spring AI 2.x and MCP SDK APIs differ from 1.x** → every call site is checked against the 2.1.0-RC2 sources while implementing (`McpMeta` null when no `_meta` is sent, `McpClientCustomizer` generics, resource-method `McpMeta`).
