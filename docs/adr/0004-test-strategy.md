## Context

The scaffold shipped build tooling and no test (ADR-0002, "Deferred tests" T1-T9). Every later change in `ROADMAP.md` is test-first and needs a ready harness: one backend test context with a real PostgreSQL and a model that needs no API key, so tests are fast, offline and deterministic. This ADR records how the tests are built. It replaces the plan in ADR-0002; the rest of ADR-0002 stands.

## Decision

### Backend: one shared context

- Every backend integration test class carries the single meta-annotation `@IntegrationTest`: `@SpringBootTest(webEnvironment = RANDOM_PORT)` with the shared test properties, `@AutoConfigureRestTestClient`, `@Import(TestInfrastructure)` and two JUnit extensions: one resets the fake model before each test, the other (`SingleContextGuard`) fails a test class that runs in a different application context than the first one seen. The annotation is the whole context cache key, so all test classes share one cached context and start the container once. The guard keeps the first context in an `AtomicReference` (`SingleContext`), compares by identity and, whatever the class order, fails every class whose context differs from the first one registered, naming it and the first class (it cannot tell which of the two customises the context; the architecture rules below name the offending class); `SingleContextTest` unit-tests it. Support code lives in the test package `...backend.testsupport`.
- `RANDOM_PORT` with `RestTestClient` bound to the real server (not MockMvc): later streaming tests need real socket semantics for event order and flushing. Cost: no per-test transaction rollback.
- Tests run sequentially against one database and one fake model. Tests that write data use unique keys and clean up; schema experiments use a uniquely named scratch schema.
- Dependencies: `spring-boot-starter-webmvc-test` replaces `spring-boot-starter-test`; `archunit-junit6` (ArchUnit 1.5.1) and `exposed-migration-jdbc` (same version as Exposed) are added in test scope; versions are in `gradle/libs.versions.toml`.

### Real PostgreSQL

`TestDatabaseTest` asserts that the shared datasource URL is the container's, so the tests pass with the compose database stopped. `TestInfrastructure` declares a `@ServiceConnection` Testcontainers `PostgreSQLContainer("pgvector/pgvector:pg18")` with the concrete return type. Datasource, Flyway and Exposed receive it through the connection details, as in production. `PostgreSQLContainer` accepts the pgvector image without a compatibility declaration, so the "image declared compatible with `postgres`" note of ADR-0002 is obsolete. The image name is duplicated in `compose.yaml` and the test infrastructure, with a comment pointing at the compose file.

### No real model in tests

- The shared context runs with `spring.ai.model.chat=none`, so the Anthropic auto-configuration backs off and the single `ChatModel` bean is a scripted `FakeChatModel` (test sources; Spring AI ships none). The key property is a placeholder and `spring.ai.anthropic.base-url` is `http://localhost:1`, so a flipped switch still reaches nothing.
- `FakeChatModel` scripts one ordered queue for blocking and streamed calls: text, bare JSON for structured output, tool-call requests and chunked text. It records every prompt, resets between tests (script, prompts and generated tool-call ids) and fails loudly ("script exhausted", with the prompt) when the script is empty. Its `getOptions()` returns tool-calling options so the tool loop executes tools. Its self-tests go through the real `ChatClient`.
- `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`, `ANTHROPIC_BASE_URL` and every `SPRING_AI_*` variable (Spring relaxed binding maps them onto `spring.ai.*`) are removed from the Gradle test environment, guarded by `CredentialIsolationTest`, so a developer key never reaches a test JVM.
- The Anthropic wiring (model `claude-haiku-5-5` from the committed `application.yaml`, construction without key or network) is tested with an `ApplicationContextRunner` over the two relevant auto-configurations, loading the committed `application.yaml` through `ConfigDataApplicationContextInitializer` (`org.springframework.boot.test.context`), outside the shared context. Accepted gap: the full application with the real model and no key is no longer started by a test.
- Only the future `evaluation` change may call a real provider, in a separate task.

### Backend tests

- Health: `GET /actuator/health` is `UP` with the `db` component `UP`; the context chat client builder is backed by the fake; only actuator and `/error` mappings exist.
- Flyway state: no pending migration, `migrate()` is a no-op, no application table while no migration exists.
- Migration history: on a scratch schema, replay from empty succeeds and an edited applied migration fails validation; the real `db/migration` directory is replayed too. Test migrations live in a test-only location that Boot does not scan.
- Schema agreement: tables are discovered with ArchUnit's class importer below `<root>.persistence.tables` (the root package derived from `BackendApplication`; abstract base tables are skipped, a concrete non-object `Table` fails loudly), and `MigrationUtils.statementsRequiredForDatabaseMigration` must be empty. A committed test with a fixture table that has no migration (`UnmigratedProbeTable`) proves the check detects a missing migration, and a fixture with an abstract base table (`AuditedBaseTable`) proves that shared-column base tables do not fail discovery. With the real package empty, this check and the Flyway-state checks are trivial until the first table exists; each carries a comment saying so, and the empty-table check in the Flyway-state test is guarded by `assumeTrue` on an empty migration list, so it is skipped (not failed) once the first migration exists. Nothing forces its replacement: the change adding the first migration must do it (see Consequences).
- Architecture (ArchUnit): no class outside `<root>.persistence.tables..` is a `Table`. A conventions test (`TestConventionsTest`) makes the single-context decision executable: slice annotations and `@SpringJUnitConfig` (anything meta-annotated with `BootstrapWith` or `ContextConfiguration`) are rejected outside `@IntegrationTest`; no class or field carries `@MockitoBean(s)`, `@MockitoSpyBean(s)`, `@TestBean`, `@DirtiesContext`, `@TestPropertySource`/`@TestPropertySources`, `@ActiveProfiles`, `@ContextConfiguration`, `@ContextHierarchy`, `@ContextCustomizerFactories`, `@WebAppConfiguration` or `@SpringBootTest` (`@TestBeans` does not exist in Spring Framework 7.1) (except the `@IntegrationTest` annotation itself); no method carries `@DirtiesContext` or `@DynamicPropertySource`; no `@IntegrationTest` class carries another annotation that is, or is meta-annotated with, any context-configuring or customising annotation (`@Import`, `@ImportAutoConfiguration`, `@PropertyMapping`, the customisation list above, `@BootstrapWith`; so `@AutoConfigureMockMvc`, `@AutoConfigureTestDatabase` and `@SpringJUnitConfig` are rejected), and no `@Configuration` or `@TestConfiguration` class is nested in an `@IntegrationTest` class (the rule selects all configuration classes, so it is never vacuous). The rule fields are snake_case because ArchUnit uses the field name as the test name (`archunit.properties` turns the underscores into spaces; detekt ignores `@ArchTest` for `VariableNaming`). Tests must run sequentially (one fake model, one database); this is noted in the KDoc of `@IntegrationTest` and `TestConventionsTest`.

### Secrets scan

A `SecretScanner` over a directory tree (test sources, tested against temp directories) finds provider-shaped keys, tokens, private-key headers, JWT-shaped values, `Bearer` tokens and assignments (`:` or `=`) to names containing `api key`, `secret`, `token` or `password` (also `passwd` and `credential`) whose value is one quoted literal (whitespace allowed) or a bare token at the end of the line, including `{noop}...` values, and URL userinfo with a literal password. It scans every text file in the working tree, tracked or not, except the directories `build`, `.gradle`, `.git`, `.idea`, `.kotlin`, `node_modules` and `.claude/worktrees`, a deny-list of binary extensions, files with a NUL byte in the first 8 KiB (checked before the rest is read), and the local-only `.env`, `*.key` and `.claude/settings.local.json`; excluded directories are not entered while walking; files are decoded leniently as UTF-8. Two kinds of rule: shape rules (`sk-ant-` and generic `sk-` keys, AWS and GitHub tokens, JWTs, private-key headers, URL userinfo with a literal password, also when the user part is a whole `${...}` placeholder, with or without default; Spring Security encoded-password prefixes `{noop}`, `{bcrypt}`, `{pbkdf2}`, `{scrypt}`, `{sha256}` and `{argon2}` followed by a literal, and `Bearer` followed by a 16+ character token) apply to every scanned file regardless of key; the assignment rule depends on the file kind. In every file that is not source, quoted and bare values are checked, so `password: kaiju.demo` is a finding; in yaml, yml, properties and env files a name at the start of a line (optionally after `- ` or `export `) takes the rest of the line, up to a ` #` comment, as its value (`password: pa;ss(word) 42`). In source files (`.kt`, `.kts`, `.java`, `.gradle`, other code) only quoted string literals are checked (a quoted literal assigned to a `password` property is a finding, also with a Kotlin type annotation (`val password: String = "..."`); `val token: String`, `lateinit var apiKey: String` and `val token = chunk.result.output.text` are not values, and neither is a quoted value that is itself a credential reference, an env-var name or a property path of three or more segments that contains a credential word (`"ANTHROPIC_API_KEY"`, `"spring.ai.anthropic.api-key"`)). Not read as assignments: prose, calls, `true`/`false`, well-known OAuth words (`Bearer`, `Basic`, `Authorization`, `client_secret_basic`, `client_secret_post`, `private_key_jwt`, `none`), plain URLs (no userinfo, query or fragment; an embedded `?client_secret=` is still found), numbers and durations next to a name that is not a password, secret, api key or credential (`DB_PASSWORD=20251119` is a finding) the plural `tokens` (`max-tokens`) and, next to a name that is only a token (no password, secret, api key or credential part), a value shorter than 12 characters or with whitespace, which is model token text (`"token":"Hel"`; `access_token: abc123def456` is a finding). A `${VAR}` placeholder without default is harmless; a `${VAR:default}` or `${VAR:-default}` default (greedy, nested braces allowed) that is not the documented literal is checked recursively with the same value rules (`${TTL:5m}` passes, `${DB_PASSWORD:${LEGACY:hunter2}}` does not). The only allowed values are the documented local `demo` literals, and only for their own keys (`DB_USER`, `DB_PASSWORD`, `POSTGRES_USER`, `POSTGRES_PASSWORD`). Deliberately not detected: names containing a space, multi-line values, escaped JSON inside a Kotlin string (`"{\"token\":\"Hel\"}"`), bare values in source files, a value with spaces or punctuation after a name that is not at the start of a line (or in a file that is not yaml, yml, properties or env), a short value (under 12 characters) next to a token-only name, and a Kotlin type annotation that is not a plain, generic or nullable type name (`val password: () -> String = "..."`). A repository test tagged `secrets-scan` runs as the Gradle task `secretsScan` (it tracks no inputs, because the scanned set cannot be declared exactly, so it runs on every build and takes about a second); the ordinary `test` task excludes the tag; `check` depends on `secretsScan`.

### Desktop

- Pure test of the theme resolution and colour tokens.
- Compose UI semantics test on `App()` (name and placeholder shown, no controls), with the non-deprecated v2 entry point and no JUnit 4.
- Off-screen render tests of `App` in forced light and dark appearance and of a gallery of all `D*` components in both themes (`components draw with the active theme's colours`); blank means at most one distinct colour in a 50x50 grid of sampled pixels, and background pixels are compared with the colour tokens; the gallery also asserts that the pixel at a known position inside the `DCard` padding equals the theme's `surface` colour. The helper is adapted from the author's own project oculi2 (MIT, same author).
- One production seam: `App(themeOverride: ThemeMode? = null)`; the application entry point is unchanged.

### `check` includes the tests

`check` runs static analysis and the tests in every module, and `:backend:check` also runs the repository-wide `secretsScan` (root `check` includes it); the backend part needs a running Docker daemon. A separate source set or tag for Docker-backed tests was considered and rejected: it splits the definition of done.

## Alternatives

- Keep the real Anthropic model next to a fake (`@Primary`): rejected, a callable real model stays in the context; `chat=none` leaves exactly one model.
- MockMvc instead of a real port: rejected for the streaming reason above.
- `@MockitoBean` or per-class contexts: rejected, they multiply contexts and slow every run.
- H2 or an embedded database: rejected, pgvector and PostgreSQL behaviour are the point.
- Secrets scan as a build-script or `build-logic` task: equivalent coverage, but the scanner would not be testable code.
- Amending ADR-0002 in place: rejected; this ADR supersedes the named parts and ADR-0002 keeps its history with a status note.

## Consequences

- Docker is a hard requirement of `check` and `build`, stated in the README. `:desktop:test` needs none.
- Later backend tests reuse `@IntegrationTest`, `FakeChatModel` and the isolation rules, and extend the fake when they need more (for example token usage). Changing the web environment or the shared properties later touches every test.
- Release-candidate behaviour of the fake's dependencies (`getOptions()`, tool-calling advisor, `RestTestClient`) may move before GA; the fake and the annotation absorb it.
- Desktop render tests are evidenced on macOS; on Linux skiko needs fontconfig and freetype, and no CI exists yet.
- The first table or migration must replace the empty-table assertion in the Flyway-state test and may tighten the schema-agreement check.
- The secrets scan reads text files only (binary files are skipped) and matches known key shapes and credential-named assignments; secrets in other, encoded or multi-line forms are not found.

## Module `core-mcp` (addendum 2026-11-20, change `core-mcp-claims`)

`core-mcp` copies the backend's pattern, slimmed to what a module without a chat model needs.

- **Copied:** one shared context through the single meta-annotation `@CoreMcpIntegrationTest` (`@SpringBootTest(webEnvironment = RANDOM_PORT)` bound to `127.0.0.1`, plus `@Import(TestInfrastructure)`), a real PostgreSQL from the compose image `pgvector/pgvector:pg18` by `@ServiceConnection`, sequential tests, the schema agreement check (tables discovered from the module's `persistence.tables` package, `MigrationUtils` must require nothing) and the first, table-independent Flyway-state check (nothing pending, migrating again executes nothing), and the ArchUnit rule that tables live only in the tables package.
- **New:** MCP tools and resources are tested end to end through the MCP SDK client (`McpTestClient`) over Streamable HTTP against the running server; the business rules are tested on the domain service beans against the real database, without MCP. Committed configuration (port 8081, the `core` URL, `generate-ddl: false`) is read from `application.yaml` directly, because `RANDOM_PORT` overrides `server.port` in the context.
- **Left out, and why:** `SingleContextGuard` and the full `TestConventionsTest` (overkill for one small module; replaced by one ArchUnit rule, below); fixture tables that prove the schema check detects a missing migration (proven once in the backend with the same helper logic); credential isolation (no provider, no key); `FakeChatModel` (the module has no chat model, and a test asserts that no `ChatModel` bean exists); `MigrationHistoryTest` (one migration directory; the schema agreement test already applies all migrations to an empty database); and the rule "use unique keys and clean up": there is no test cleanup in `core-mcp`. Tests that write data use only the sandbox policy `KP-9000` and the claims they create, the container is fresh on every run, and exact counts are asserted only over rows no test writes (customers, policies, claims on other policies, payouts of the seeded claims).
- **The ArchUnit context rule:** no class that is not an annotation (test classes included, so the rule is never vacuous) may carry `@SpringBootTest`, `@TestPropertySource`, `@Import`, `@ContextConfiguration`, `@ActiveProfiles` or `@DirtiesContext` directly; `@CoreMcpIntegrationTest` is exempt because it is an annotation.
- **Remaining gap, a review item only:** the rule sees class-level annotations. `@MockitoBean` and `@MockitoSpyBean` on fields, a `@DynamicPropertySource` method or a nested `@TestConfiguration` can still change the context, and nothing fails when one appears; reviewers check for them.

## Addendum 2026-11-20: fake core tools (change `mcp-tools-and-confirmation`)

The backend gains an MCP client for the core tools of `core-mcp`. The single shared context stays, the same way `policy-rag` added the fake embedding model.

- **MCP client off.** `@IntegrationTest` sets `spring.ai.mcp.client.enabled=false`: no MCP client, transport or tool-callback provider bean exists, and nothing in the suite touches the network.
- **Fake core tools under the real bean name.** `TestInfrastructure` declares `FakeCoreTools` (`@Tool getClaim` and `@Tool issuePayout`, both with a `ToolContext` parameter, which `MethodToolCallback` needs to hand over the context) and a `ToolCallbackProvider` bean named `mcpToolCallbacks`, so the adjuster's `@Qualifier("mcpToolCallbacks")` resolves to it. The fake records every call with its arguments and tool context, can be told to make `issuePayout` throw a given exception and to make the tool listing throw (an unreachable core), and sets no `requiresConfirmation`: confirmation must come from the committed property, as for the real MCP tool.
- **Reset.** `FakeChatModelReset` empties `FakeCoreTools` (calls and both failures) before each test, together with the fake chat model.
- **Environment scrub.** The Gradle `Test` tasks also remove `CORE_MCP_URL`, guarded by `CredentialIsolationTest`, so `McpClientWiringTest` sees the committed default URL. That test runs outside the shared context (`ApplicationContextRunner` over the MCP client, Streamable HTTP transport, tool-callback and tool-calling auto-configurations with the committed YAML and `McpClientConfiguration`, like `OllamaWiringTest`): the connection `core` and its URL, one `SyncMcpToolCallbackProvider`, startup without a core, tool names kept as published, and the `ToolCallingManager` gating `issuePayout` but not `getClaim`.
- **Accepted gap.** `SyncMcpToolCallback` itself (arguments to `CallToolRequest`, `isError` results to text, the tool context as MCP `_meta`, the lazy `initialize`) never runs in the suite. `core-mcp`'s own tests cover the server; only the manual smoke of the change (a running `core-mcp`, Ollama and an Anthropic key) covers the wire between the two. A fake MCP server inside the backend context and starting `core-mcp` out of process were rejected (the client transport is built before the server port exists; a second application with its own database container).
