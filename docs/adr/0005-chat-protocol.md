## Context

`chat-streaming` is the first feature that crosses the boundary between `backend` and `desktop`: the claimant types a message in the desktop window and the backend streams the model's answer back. Both sides must agree on the request and on the events of the stream, and later waves add events (todo updates, claim cards, tool calls, confirmation requests, roadmap R6). ADR-0001 says shared code needs a new module and an ADR; roadmap question Q1 asks whether that is a shared `chat-protocol` module or duplicated DTOs.

## Decision

### A shared library module `chat-protocol` (resolves roadmap Q1)

- A third Gradle module `chat-protocol`, package `dev.frederikpietzko.springaidemo.chatprotocol`, holds `Persona`, `ChatRequest`, the sealed `ChatEvent` and one `Json` instance (`ChatJson`). It applies the `demo.kotlin-jvm` convention plugin (detekt, JUnit 6, power-assert, part of the root `check`) and the kotlinx.serialization compiler plugin, and declares exactly one library: `api(kotlinx-serialization-json)`.
- `backend` and `desktop` both use `implementation(project(":chat-protocol"))` and still do not depend on each other.
- `chat-protocol` is a **shared library module, not a runtime module**: it has no process, no port and no entry point. Roadmap decision 3 ("Four modules": `backend`, `desktop`, `core-mcp`, `auth-server`) describes the runtime topology, and it stays unchanged; ADR-0003's port table needs no entry.
- The module's only dependency is checked when the build file is reviewed (and with `inspect_dependencies`); there is no architecture test, because the compile classpath makes a Spring, Compose or Ktor import a compile error anyway.

### Event hierarchy and JSON form

```kotlin
@Serializable enum class Persona { CLAIMANT, ADJUSTER }
@Serializable data class ChatRequest(val persona: Persona, val message: String)

@Serializable
sealed interface ChatEvent {
    @Serializable @SerialName("text-delta") data class TextDelta(val text: String) : ChatEvent
    @Serializable @SerialName("done") data object Done : ChatEvent
    @Serializable @SerialName("error") data class Error(val message: String) : ChatEvent
}
```

- Wire forms: `{"type":"text-delta","text":"Hel"}`, `{"type":"done"}`, `{"type":"error","message":"..."}`, and the request `{"persona":"CLAIMANT","message":"Hi"}`. `type` is kotlinx's default class discriminator; an unknown `type` or persona fails to decode.
- `ChatEvent.toJson()` encodes through the sealed base serializer and `chatEventFromJson(json)` decodes; nobody encodes through a subclass serializer, which would drop `type`.
- Gotchas (also in the KDoc of `ChatEvent`): no event property may be called `type`; write `ChatEvent.Error` because a bare `Error` is `kotlin.Error`; the delta field is `text`, never a name containing `token` (the secrets scan of ADR-0004 treats such names specially).

### Extension rule

- The change that first emits a new event adds its subclass with a `@SerialName` to `chat-protocol`. New fields get defaults, so older payloads still decode.
- A stream ends with exactly one terminal event, today `Done` or `Error` (a JVM error, which is not an `Exception`, is rethrown instead and breaks the stream; see Transport and Desktop client). A later change may add another terminal event (for example `ConfirmationRequest` for roadmap R6).
- Both sides compile against the one sealed type, so the desktop's exhaustive `when` stops compiling until a new event is handled. There is deliberately no "unknown event" fallback.
- Only what `chat-streaming` emits is defined. `TodoUpdate`, `ClaimCard`, `ToolCall` and `ConfirmationRequest` arrive with their changes.

### Persona selection

The persona travels in the request body, and there is one chat endpoint for every persona. `CLAIMANT` is answered by the claimant chat. `ADJUSTER` is a valid protocol value that is not available yet: the backend answers it with a single `Error` event and never calls the model, and the desktop shows the option disabled.

### Transport: server-sent events from a Kotlin `Flow`

- `POST /chat` (`consumes = application/json`, `produces = text/event-stream`) takes a `ChatRequest` and returns `Flow<ServerSentEvent<String>>`. Every other method on `/chat` is a 405.
- The model reply is Spring AI's `chatClient.prompt().user(message).stream().content()` `Flux`, bridged with `kotlinx.coroutines.reactive.asFlow()`. Spring AI 2.1 has no `Flow` API of its own. Spring MVC accepts a `Flow` return value only with `kotlinx-coroutines-reactor` on the classpath (it registers the coroutine adapters in `ReactiveAdapterRegistry`); the backend adds it without a version, the Boot BOM manages it.
- The element type `ServerSentEvent` selects Spring MVC's SSE path: no async timeout and a flush after every event. Each event's data is the **pre-encoded** JSON string of one `ChatEvent` (`event.toJson()`), written by `StringHttpMessageConverter` as UTF-8 (Boot's default `spring.http.converters.string-encoding-charset`). A non-String payload would be serialized by the runtime subclass and lose `type`. No SSE `event:` name is set; the client reads `type` from the JSON.
- Terminal-event rule on the backend: `onCompletion { cause -> if (cause == null) emit(Done) }` followed by `catch { log.warn(...); emit(Error("The claims desk is unavailable.")) }`. The order matters: an `onCompletion` after `catch` would see a normal completion and add `Done` after the `Error`. The error text is generic; the exception is only logged. Only `Exception`s are mapped: any other `Throwable` (a JVM error) is rethrown from the `catch` and breaks the stream without a terminal event (project rule "no catching `Throwable`"). A cancelled collection (the client disconnected) has a cause and emits nothing.
- Failures before the stream stay plain HTTP: malformed JSON or an unknown persona is a 400 from kotlinx decoding (verified: the 400 is resolved from kotlinx's `Persona does not contain element with name 'AUDITOR'`, not from Jackson). A blank message is not validated.

### The audit advisor

- `AuditAdvisor : StreamAdvisor` on the claimant `ChatClient` (order `HIGHEST_PRECEDENCE + 100`, outside the tool loop at `+300`) records one `AuditEntry(userMessage, outcome, replyChars, millis)` per streamed call that ends into the in-memory `AuditTrail` (newest 100 entries, thread-safe) and logs one line with lengths and duration, never the message text.
- It wraps the downstream `Flux` with `ChatClientMessageAggregator().aggregateChatClientResponse(...)`, whose callback fires on completion even when no chunk carries a finish reason. The aggregator never calls back for a failed stream (it only logs "Aggregation Error"), so a `doOnError` on the same `Flux` records the failure (`replyChars` 0: the partial reply is not aggregated). A stream cancelled by the client triggers neither and is not audited.
- It does not extend `BaseAdvisor`: `BaseAdvisor.after()` runs only on chunks with a finish reason (the test fake's chunks have none, so it would never fire) and wraps stream errors in `IllegalStateException`. There is no `CallAdvisor` branch: nothing in this change makes a blocking call, so it would ship untested. The change that adds blocking calls adds it with its own test.
- The audit trail holds user text in memory. Demo only; real redaction belongs to `injection-guardrails` (not done by `injection-guardrails`, see the status note).

### Desktop client

- Ktor client 3.6.1 with the CIO engine and the `SSE` plugin (part of `ktor-client-core`). `HttpChatApi(baseUrl, client = HttpClient(CIO) { install(SSE) })` posts the request as JSON (`client.sse("$baseUrl/chat", request = { method = Post; contentType(Json); setBody(...) })`) and emits each event's `data` decoded with `chatEventFromJson` inside a `flow {}`. It is `AutoCloseable`; `main` creates the one instance and closes it when the window closes. CIO over the Java engine: no `java.net.http` module concern for a later packaged build; the CIO request timeout does not apply to SSE requests, so long answers are not cut off; `SSEConfig` defaults (`maxReconnectionAttempts = 0`) never retry a POST.
- Error mapping, verified in the 3.6.1 sources (`plugins/sse/builders.kt`): Ktor wraps every failure, including `java.net.ConnectException`, in `SSEClientException`, and also wraps exceptions thrown inside the session block. So the type does not tell the cases apart: `SSEClientException` with `response == null` means "Backend not reachable"; a non-null `response` (wrong status or content type) means "The backend answered with an error"; a `SerializationException` anywhere in the cause chain means "The backend sent an unreadable answer". Every failure that is an exception becomes exactly one `ChatEvent.Error` with a short fixed text, so the screen only ever sees events and the application starts without a backend. `CancellationException` is rethrown, never mapped. JVM errors (anything that is not an `Exception`) are rethrown too; they are searched in the cause chain, since Ktor wraps them in `SSEClientException` as well.
- `interface ChatApi { fun send(request: ChatRequest): Flow<ChatEvent> }` is the seam. `ChatViewModel(api)` is a plain class (no androidx `ViewModel`) holding a `StateFlow<ChatState>`; it stops collecting at the first terminal event and treats a stream that ends without one as a dropped connection ("The connection closed before the answer was complete.").
- Second production seam of `App`: ADR-0004 named `App(themeOverride)` as the only seam. `App(chatApi: ChatApi, themeOverride: ThemeMode? = null)` adds the `ChatApi` parameter, deliberately without a default, so no test or caller silently gets a real HTTP client. Tests pass a `FakeChatApi`.
- The backend address is `BACKEND_URL`, default `http://localhost:8080` (ADR-0003 port), read through `backendBaseUrl(System::getenv)`.
- Testing: the view model and the screen are tested with the fake `ChatApi`; `HttpChatApi` is tested against a JDK `com.sun.net.httpserver.HttpServer` on a free port (200 with events and the recorded POST, non-ASCII data, status 500, undecodable event, closed port, JVM error). Ktor's `MockEngine` is not used: it does not declare the SSE capability in 3.6.1, so the engine rejects an SSE request.
- Ktor pulls `slf4j-api` without a provider and prints a one-time "No SLF4J providers" warning; accepted for a demo (`slf4j-nop` would silence it).

### Accepted test gaps

- The backend tests read the finished response body over a real socket, so they prove event order, framing, charset and terminal events, but not that each event is flushed as it is produced. Incremental delivery is shown manually with `curl -N` (README, "Chat endpoint").
- The client test serves a finished body, so Ktor's chunk timing is not covered either; scrolling the conversation to the newest message is checked by eye only; a stream cancelled by the client leaves no audit entry and has no test.

## Alternatives

- Duplicated DTOs in `backend` (Jackson with polymorphism annotations) and `desktop` (kotlinx): rejected. Two definitions drift, and the desktop loses compile-time exhaustiveness over the events.
- A persona per path (`/chat/claimant`, `/chat/adjuster`): rejected, later waves reuse one endpoint and one stream format.
- A 4xx status for `ADJUSTER`: rejected, it would be a second error path the desktop has to parse; one `Error` event uses the path that already exists.

## Consequences

- kotlinx.serialization is on the backend classpath, so Spring MVC registers its `KotlinSerializationJsonHttpMessageConverter` for `@Serializable` types ahead of Jackson. `ChatRequest` is decoded by kotlinx with the default `Json` (unknown keys and unknown personas give 400, as on the desktop); actuator and every other type stay on Jackson. `spring-boot-starter-kotlinx-serialization-json` is not added. A later controller that takes a `@Serializable` type gets kotlinx too.
- Adding an event is a change to `chat-protocol` plus both sides, in one change, guided by the compiler.
- ADR-0001's layout gains a third module; ADR-0003's module and package tables gain `chat-protocol` / `chatprotocol` (status-line notes on both).

## Addendum 2026-11-20: `claim-intake`

- New event `ClaimCard` (`{"type":"claim-card","policyNumber":"KP-1001","district":"HARBOUR","incidentAt":"2026-11-19T15:00:00Z","kaijuClass":3,"description":"...","damageItems":[{"category":"VEHICLE","description":"Car roof","amountMinor":800000}]}`): a prepared claim for the claimant to check and confirm. It is not terminal; a `Done` follows. District and category are plain strings (the module depends only on kotlinx-serialization-json), the incident time is an ISO-8601 string with offset, amounts are whole minor units. The total of the items (`totalMinor`) is derived on the event and not part of the JSON.
- The chat request gains `action: ChatAction = MESSAGE` as its last field (`PREPARE_CLAIM`, `CONFIRM_CLAIM`). The default is left out of the JSON, so every existing request keeps its wire form; an unknown action fails to decode (400). For the claimant, `MESSAGE` is answered by the claimant agent as before, the claim actions by the claim intake, and their message is ignored. `ADJUSTER` ignores the action (see the addendum on the adjuster agent): the claim actions belong to the claimant. There is still one chat endpoint.
- `ChatEvent.isTerminal` answers, from an exhaustive `when`, whether an event ends the stream (`Done` and `Error` do, `TextDelta` and `ClaimCard` do not). A new event cannot be added without deciding it. The desktop collects with `transformWhile { !it.isTerminal }`, which resolves the `chat-streaming` follow-up "`ChatViewModel` treats every non-`TextDelta` event as terminal".
- The backend's terminal-event rule is unchanged and is now one private extension of the controller, used by the claimant reply and both claim actions.
- Not audited: the claim intake makes a blocking structured-output call on a private `ChatClient` without advisors. Unlike the sentence "The change that adds blocking calls adds [the `CallAdvisor` branch] with its own test" above, this change deliberately adds no audit branch: blocking intake calls are not audited until `injection-guardrails`, where redaction and audit belong together (not done by `injection-guardrails`, see the status note) (the policy RAG's `CoverageQuestions` already went without one).

## Addendum 2026-11-20: adjuster agent and payout confirmation (change `mcp-tools-and-confirmation`)

Roadmap risk R6 asked how a streaming tool loop pauses for a human decision. It ends the stream and resumes with a new request.

- **Persona `ADJUSTER`** is answered by the adjuster agent (`backend/adjuster`): its own system prompt and the core tools of `core-mcp` through the Spring AI MCP client. It no longer answers with a single `Error`, and the desktop lists `Adjuster` as selectable.
- **`ConfirmationRequest(confirmationId, toolName, arguments)`** (`"type":"confirmation-request"`) is the third terminal event. When the model calls a tool that needs confirmation (`issuePayout`, configured by name with `spring.ai.tools.confirmation.tools`), Spring AI's tool loop pauses: none of the reply's tool calls runs, and the last streamed chunk carries the calls and the metadata key `ToolCallDecisions.AWAITING_DECISION_METADATA_KEY`. The adjuster streams `chatResponse()` (not `content()`, which hides the pause) and turns that chunk into the event, naming the first waiting call. Neither `Done` nor `Error` follows it.
- **`POST /chat/decisions`** takes `ConfirmationDecision(confirmationId, approved)` (`{"confirmationId":"...","approved":true}`, a new `@Serializable` type in `chat-protocol`) and streams the continuation with the same terminal rules; `GET` on it is a 405. The paused reply stays on the server (`PendingConfirmations`, an in-memory map keyed by a UUID), so the client never sends or changes tool calls. A decision takes its entry out, so a replay or an unknown id answers one `Error` event ("Nothing is waiting for this decision.") and runs nothing. A restart forgets the pending entries.
- **Approve and deny.** Spring AI's loop keeps no state and has no cancel: the decision builds one `ToolCallDecision` per call of the paused reply (`allow`, or `deny` with the text "The adjuster did not approve this payout."), runs `ToolCallingManager.executeToolCalls(prompt, reply, decisions)` with a prompt that carries the core tools and the tool context again, and streams a new model turn over the resulting conversation. Approve runs the payout once; deny runs nothing and the model writes a closing reply to the denial text. The continued turn may pause again. (Corrected by "Addendum 2026-11-20: adjuster todo list": deny now stops only the calls that wait for a decision.)
- **Stateless-loop consequences.** The resumed conversation is only the original user message, the paused tool-call reply and the tool results: tool rounds that ran before the pause in the same turn (such as a `getClaim`) are not replayed, and no system message is stored (the client adds its own). The adjuster has no conversation memory. (Corrected by "Addendum 2026-11-20: end-to-end fixes": the tool rounds before the pause are now replayed.)
- **Terminal rule on the backend.** The controller now collects the agent's events and adds `Done` only after a reply that ended in text (or nothing); after a `ConfirmationRequest` or an error event of the agent it adds nothing. (Superseded by "Addendum 2026-11-20: adjuster todo list": `Done` follows every completed reply whose last event is not terminal; since the parallel tracks were merged, this one rule, based on `ChatEvent.isTerminal`, ends the claimant reply, the claim actions and the adjuster reply alike.) Failures are mapped by the same `catch` as before (generic `Error`, cause logged, JVM errors rethrown). Request building (including listing the MCP tools, which is the MCP client's first connection) happens inside the adjuster's `flow`, so an unreachable core is an `Error` event, not an HTTP 500. A tool's runtime exception or a domain error of `core-mcp` reaches the model as the tool result; only a checked exception or a protocol-level `McpError` fails the reply.
- **Desktop.** `ChatApi` gains `decide(decision)`; `ChatState.pendingConfirmation` holds the open request; `ChatViewModel` ignores `send` while one is pending, and `decide(approved)` posts one decision, clears it and appends the continuation to the same reply through the same collect function as `send`. The screen shows a confirmation panel with the tool name, its arguments and `Approve` and `Deny` buttons between the conversation and the input row.

## Addendum 2026-11-20: adjuster todo list (change `agent-todo-and-skills`)

- **`TodoUpdate(todos)`** (`{"type":"todo-update","todos":[{"content":"Check coverage","status":"IN_PROGRESS","activeForm":"Checking coverage"}]}`) carries the adjuster's whole todo list after one of its `TodoWrite` calls, in the model's order. `TodoItem(content, status, activeForm)`, `TodoStatus` is `PENDING`, `IN_PROGRESS` or `COMPLETED`. Every update replaces the list before (the library always sends the whole list, so there are no per-item deltas). It is not terminal (`isTerminal` is `false`). An invalid list (for example two items in progress) is rejected by the tool and reaches the model as the tool result; no event is sent. The library and its wiring are ADR-0007.
- **`Done` rule on the backend.** The controller adds `Done` after every completed adjuster reply whose last event is not terminal (`last?.isTerminal != true`): after text, after a todo update, or after nothing. After a `ConfirmationRequest` or an error event of the agent it still adds nothing. This supersedes the earlier addendum's "Terminal rule on the backend" sentence "`Done` only after a reply that ended in text (or nothing)": a reply whose last event is a todo update (an empty final text) would otherwise end without a terminal event.
- **Deny stops only the calls that wait for a decision.** This corrects the earlier addendum's "Approve and deny" bullet, which says the decision builds one `ToolCallDecision` per call from the approval and that deny "runs nothing". The decision now applies approve or deny only to the calls in `ToolCallDecisions.awaitingDecision(reply)` and allows every other call of the paused reply. Approve still runs every call once; deny gives the waiting calls the denial text and runs the others normally (`TodoWrite`, `getClaim`, `Skill`). The prompt of the resume carries the core tools, the request's own `TodoWrite` tool and the `Skill` callback, because an allowed call runs only with a tool of the prompt. Without this, a reply that called `TodoWrite` and `issuePayout` together failed on approve and handed the payout denial text to the todo call on deny.
- **Stateless resume.** A `TodoWrite` call among the paused calls sends its update on the decision's stream, before the continued reply. The model of the continued reply does not see its earlier todo writes (the stateless-loop consequence above); the desktop keeps showing the last list until a new update arrives.
- **Desktop.** `ChatState.todos` holds the latest list; `ChatViewModel` replaces it on every `TodoUpdate` and clears it on a new conversation, an opened conversation and a persona switch. The screen shows a todo panel to the right of the conversation while the list is not empty: a marker per status (`[ ]`, `[>]`, `[x]`), the active form of the item in progress and the content of the others.

## Addendum 2026-11-21: claims-analytics

- New event `AnalyticsTable(title, columns, rows)` (`{"type":"analytics-table","title":"Payouts by district","columns":["District","Payouts"],"rows":[["HARBOUR","3"]]}`): a table of numbers a tool computed. Every cell is a string (amounts are whole minor units written as digits), so the desktop needs no domain knowledge and no chart code. It is not terminal; the model's text and a `Done` follow, and `isTerminal` decides it in its exhaustive `when`.
- **Who emits it.** The adjuster, when the model calls the core tool `payoutStats` and the call succeeds: the title is `Payouts`, plus ` by district` or ` by kaiju class` when grouped, the columns are the grouping name (else `Group`), `Payouts`, `Total paid`, `Average paid`. The event comes before the text the model writes after the tool call (a short lead-in the model writes before the call in the same round streams earlier). Other tools, failed calls and unexpected result shapes give no table, and the model always receives the tool result unchanged.
- **Why the backend captures it.** Spring AI 2.1's tool loop never streams tool results to the caller: the stream carries only the model's text and, for a confirmation, the paused chunk. So the adjuster wraps the `payoutStats` callback per request in a decorator (`TableCapture`) that hands the result string (the MCP client's `[{"text":"<core JSON>"}]`) to the reply's channel after the delegate returned; the request's `channelFlow` emits it as the event. The decorator never throws (a mapping failure is logged and gives no table), because the tool manager turns only `ToolExecutionException` into a tool result and any other exception would fail the whole reply. A `payoutStats` call inside a confirmed (resumed) batch gives no table.
- The desktop shows the table in the assistant message under the reply text, and a table-only reply does not show the "…" placeholder.

## Addendum 2026-11-20: end-to-end fixes

Found in a manual run against the real stack; the protocol is unchanged.

- **The resumed turn replays the tool rounds before the pause.** Without them the model described its own earlier calls (a status change, a claim lookup) as never having happened. The adjuster records each round's messages with a small advisor inside the tool-calling loop (`ToolCallingAdvisor.DEFAULT_ORDER + 1`, one instance per turn), and the paused turn keeps the last round's messages without the system message, which the resumed turn adds itself.
- **Approving a claim needs a confirmation too.** `updateClaimStatus` to `APPROVED` pauses like `issuePayout`, through a `ToolCallConfirmationPolicy` bean that reads the arguments (the property gates by name only, and other status changes stay unconfirmed); the event is the same `ConfirmationRequest` naming `updateClaimStatus`. A denied approval answers the model "The adjuster did not approve this call."; a denied payout keeps "The adjuster did not approve this payout."

> Note 2026-11-20 (simplification pass): the controller maps every failure of a stream to the generic `Error` event; a JVM error is no longer searched in the cause chain and rethrown. A denied tool call gets one text for every tool, "The adjuster did not approve this call.".
